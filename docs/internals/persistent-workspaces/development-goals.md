# Autonomous development goals

Users set a project objective and acceptance criteria in the existing Main conversation. This implements goal-driven continuation inside T3. No external dots installation, account, browser, or new reasoning engine is required.

`WorkspaceDevelopmentState.goal` persists the independent goal ID/revision, control state, next phase, pending Main message, step/time limits, progress fingerprint, summary and integration evidence. The optional field decodes existing migration-067 snapshots without rewriting their histories or adding another registry. The existing project command audit makes repeated authenticated `workspaceDevelopment.goal` commands idempotent. Goal control is available to authenticated environment operators; the model cannot set its own objective or raise limits.

The same manager queue owns both Owner notifications and goal continuation. It waits for the existing Main to be idle, reserves an identifiable input before dispatch, uses the selected Main model, and observes its actual session lifecycle. There is never a second native resume process. Main reports `goal-progress` with the current goal ID/revision and a continue/wait/blocked/complete outcome. Waiting requires real queued or running Owner tasks; their completion triggers the next Main turn. No timer repeatedly asks an LLM to poll status.

Pause stops new automatic turns and new queued goal Owner writers, and prevents the in-flight automated Main from submitting new work or promoting an integration. Already executing work finishes; pause is not an emergency abort. Resume is explicit. Cancel supersedes queued goal tasks and preserves running work, commits, histories and evidence. Human Owner control, freshness and integration barriers remain enforced; other areas can continue. The app and server must stay running for autonomous progress.

Limits apply to automatic Main turns and elapsed active goal time, including waiting for Owners. Paused time does not count. The time limit is checked before another Main turn starts; it does not interrupt an in-flight CLI or test at an exact second. These are not provider token/spending caps. Two reports with no new task/workspace/verification/integration evidence stop continuation. A response without a progress report blocks rather than looping. Failed/ambiguous Main delivery blocks without a blind resend.

Restart restores the goal and bindings. A persisted in-flight Main input becomes blocked for reconciliation, rather than assuming execution completed or replaying it. Explicit resume waits for the actual Main to be idle. Existing running Owner recovery still marks uncertain delivery and requires reconciliation.

Completion needs a new release-ready integration belonging to the current goal, its real test log, a clean current integration HEAD equal to the result SHA, current Owner verification revisions/generations/HEADs, no unsettled runs or human changes, and inclusion of the goal's completed task candidates. Main evaluates the meaning of the acceptance criteria and records its explanation; the service checks the concrete execution/Git evidence. A model's claim alone does not complete the goal. External publication remains outside the manager's operations.

Web and desktop expose goal input and start/pause/resume/cancel beside the existing composer. Existing authenticated environment RPC keeps remote/relay behavior independent of origins. Mobile receives the same Main and Owner conversation history but does not yet expose the goal control form. Codex and Claude use their existing provider adapters; other providers are not enabled for persistent workspace goals. Codex native Goals remains a measurement probe, not a second product scheduler.

Tests cover idempotency, busy Main, automatic continuation, waiting without polling, pause/cancel, explicit resume, limits, uncertain restart and false completion. The native demo is `node scripts/workspace-development-goal-demo.mjs <isolated-home> start`; it requires the existing two-provider workspace demo and stores only noncredential evidence in `<isolated-home>/goal-demo.json`.
