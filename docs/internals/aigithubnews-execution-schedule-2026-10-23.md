# 수집한 GitHub 전체 학습과 개발 계획표

대상은 **이번에 수집한 GitHub 주소 8,682개 전체**다. 이전 주소 104개를 같은 저장소에 연결해 공개 저장소 8,429개와 공개 확인이 안 되는 주소 149개, 총 **8,578개 검토 단위**로 관리한다. 기존에 노트를 작성한 35개와 우선순위 P1인 14개는 먼저 확인한 사례이며, 전체 검토 대상을 제한하는 기준으로 쓰지 않는다.

현재 자료 수집·원본 검증·프로젝트 기억 저장과 전체 대상 등록을 완료했다. 기존 35개 README 노트를 평가 양식에 연결했고, 14개 분야의 [표본 100개 발췌 검토](aigithubnews-pilot-screening-2026-10-23.md)를 추가했다. 전수 검토와 병행해 실제 재현된 검색·연결 초기 오류를 별도 앱에서 수정·검증하고 운영에 반영했다. [첫 업데이트 검증 기록](../operations/aigithubnews-upgrade-2026-10-23.md)에 완료 범위와 증거를 남겼다. **나머지 상세 내용 검토·소스 실험·전체 개발 과제는 계속 진행 대상**이다. 발췌 검토만으로 전체 처리량을 산정하지 않았다. [전체 검토 범위](aigithubnews-full-review-scope-2026-10-23.md), [발전 계획](aigithubnews-learning-plan-2026-10-23.md), [기존 학습 노트](aigithubnews-learning-notes-2026-10-23.md)를 연결한다. 모든 주소의 검토 묶음 배정 누락은 0개다.

## 실행 계획표

2026-10-24 3차 구현: 관련 문맥의 안내 중복을 줄이고, 전달 불명 상태를 코드·요구 변경으로 해제하지 않도록 복구 장벽을 수정했다. 출처·버전·후보 해시·집중 검사 로그·원본 복구 자료를 연결하는 프로젝트 스킬과 읽기 전용 증거 검증기를 추가했다. 같은 프로세스·DB에서 순서를 교대해 검색·문맥을 비교한 기록과 적용 범위는 [3차 업데이트 기록](../operations/aigithubnews-phase3-2026-10-24.md)에 연결한다. 전체 GitHub 상세 검토 완료 수는 변경하지 않는다.

2026-10-23 2차 구현: 사진 드롭과 프로젝트별 첨부 보존을 분리 후보에서 수정했다. 한국어 120문항 평가 도구를 만들고 실제 로컬 의미 검색·키워드 검색을 나눠 실행했다. 의미 검색 근거의 문맥 탈락, 원문 URL·기록 시각 누락을 보완했으며 기존 복구·취소·사용량 처리를 집중 회귀 검사했다. 합성 검색·근거 조건은 55/120→120/120으로 개선됐다. 답변 생성 정답률은 측정하지 않았다. 입력 토큰 증가와 지연 측정 편차, 운영 승격 증거는 [2차 업데이트 기록](../operations/aigithubnews-phase2-2026-10-23.md)에 남긴다. 전체 GitHub 상세 검토 범위와 미완료 수는 변경하지 않는다.

## 전체 기간과 첫 개발 주기의 구분

**전체 수집 목록을 4주에 모두 검토·구현한다고 확정하지 않는다.** 먼저 표본 100개를 처리해 분야별 처리량을 측정한다. 최대 200개 단위의 48개 묶음은 진행 관리 단위이며 각 원문은 개별 자료나 작은 그룹으로 읽는다. 자동 분류와 대상 등록을 실제 내용 검토 완료로 표시하지 않는다.

기존에 제시한 20작업일은 전수 평가 후 선택할 첫 T3 개발 주기의 초기 예상으로 구분한다. 해당 주기에서는 평가 기준 → 기억·문서 검색 → 작업 복구·준비·전환 → 스킬·문서 → 화면·기기 동작 → 통합 검증 순서를 사용하되, 실제 개발 항목은 전체 검토 결과로 정한다.

이미지·영상, 음성·음악, 모델 학습, 로컬 추론, 데이터·인프라, 업무 자동화, 교육 자료, 금융·전문 분야도 전체 평가와 학습 과제에 포함한다. 직접적인 T3 변경 가치 외의 연구·관련 프로젝트 활용 가치도 기록하며, 원래 요청 밖의 다른 프로젝트를 자동 수정하는 결정으로 연결하지 않는다.

## 선별 후 T3 개발의 검증 기준

다음 기준은 전수 검토에서 선택한 T3의 기억·검색·실행 개선에 적용한다. 이미지·영상·음성·모델 학습 등 다른 분야는 해당 작업의 정답·품질·자원 사용·재현성을 평가하는 자료와 기준을 별도로 정한다.

T3 검색용 한국어 120문항은 의미 검색 30개, 정정 20개, 시점 20개, 프로젝트·폴더 범위 20개, 삭제·제외 10개, 긴 기록 10개, 코드·버전 10개로 구성한다. 평가에 사용한 자료와 최종 확인용 holdout을 구분한다.

| 항목        | 초기 목표 또는 필수 조건                                                              |
| ----------- | ------------------------------------------------------------------------------------- |
| 개선 효과   | 어려운 검색 부분집합의 정답률 5%p 개선 또는 같은 정답률에서 입력 토큰 중앙값 15% 절감 |
| 검색 품질   | 전체 정답률과 Recall@5가 기준보다 떨어지지 않음                                       |
| 검색 지연   | 같은 측정 조건에서 P95 지연이 기준 대비 10%를 초과해 악화하지 않음                    |
| 범위 준수   | 프로젝트 경계 침범과 제외 자료 노출 0건                                               |
| 실행 일관성 | 중복 실행·취소 뒤 새 실행·사용량 이중 집계 0건                                        |
| 근거 추적   | 답변·수정·완료 판단에서 확인한 원문과 실행 증거를 다시 읽을 수 있음                   |

개선 효과의 수치는 앞으로 측정할 목표다. 범위 준수와 실행 일관성은 평균 점수로 상쇄하지 않는다. 의미 검색을 사용할 수 없는 조건과 사용할 수 있는 조건은 따로 기록하고 같은 조건끼리 비교한다.

## 진행 기록과 적용 범위

각 작업은 대기 → 진행 → 검증 → 완료로 기록한다. 완료에는 변경 내용, 확인한 근거, 집중 테스트·측정 결과와 남은 제약을 붙인다. 새 기능이 필요하지 않은 항목은 기존 동작의 검증 결과로 완료할 수 있다. 발견된 결함이 크면 뒤 작업의 일정을 조정하고 미완료 부분을 분명히 남긴다.

현재 코드와 기존 기능을 먼저 대조하고 필요한 부분을 수정한다. 계약 변경은 `packages/contracts`, 공통 클라이언트 동작은 `packages/client-runtime`을 기준으로 웹·데스크톱·모바일에 적용한다. 채팅·설정·명령 팔레트·단축키와 로컬·원격·relay 연결에서 관련되는 경로를 기록한다. provider에 영향을 주는 변경은 Codex·Claude·Cursor·Grok·OpenCode와 현재 등록된 추가 어댑터의 지원 여부를 확인한다.

검증은 변경 범위의 테스트·타입 검사·lint와 백그라운드 또는 headless 경로를 사용한다. 저장소 전체 검사는 별도 요청 없이 실행하지 않는다. 화면 활성화·입력 주입·PowerShell을 사용하지 않으며 현재 사용자의 권한·질문하기·조건확인·계획 선택을 유지한다.

운영 반영은 [기존 Windows 운영 절차](../operations/windows-runtime-start.md)를 따른다. 운영 데이터 홈 `E:/NewAutoUsage`와 web·backend·desktop 범위를 유지하고, 기존 관리자 예약 작업과 실행기로 실제 창을 `showInactive()`로 표시한다. 서버 응답·프로세스 토큰·창 표시·렌더링을 확인한 범위를 기록한다.
