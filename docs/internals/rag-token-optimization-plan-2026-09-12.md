# AutoUsage 장기기억 RAG·작업 토큰 최적화 계획

2026-09-12 KST의 초기 **조사·설계 명세**. 이후 승인된 구현의 현재 상태와 실제 결과는 [구현 영수증](./rag-token-implementation-2026-09-12.md)을 따른다. 이 명세의 도입 조건을 구현 완료 주장으로 읽지 않는다.
사용자 요청: X/Grok CLI로 자료를 수집하여, 사용자 명령부터 AI 작업 완료까지의 RAG와 토큰 개선 계획을 만들고 AutoUsage RAG에 보존한다.

## 1. 우선 결정

먼저 **현재 작업과 무관한 기억 주입, 중복 기록, 불필요한 재작업**을 줄인다. 이후 실제 검색 누락이 확인된 영역에 하이브리드 검색을 추가한다. RAG 전체를 C++로 다시 쓰는 일은 우선순위에 두지 않는다. 현재 검색은 SQLite FTS5이며, 허브의 C++ 행 조회 최적화는 LLM 입력 토큰을 직접 줄이지 않는다.

기존 [토큰 효율 설계](./token-efficiency-design.md)를 보완한다. 이미 구현된 [P0 사용량 계측](./token-usage-implementation.md)과 [P1 대화 인계 추출](./conversation-handoff-implementation.md)을 재사용한다. 모델·추론 수준·요청한 작업 범위·검증 책임은 유지한다. 예산 때문에 완료하지 않은 일을 완료로 처리하지 않는다.

권장 순서: **기준선/계측 보완 → 기억 선택·현재성 → 형식 복구 → 단계별 입력·도구 결과 절약 → 협업 인계 → 검색 품질 확장**. 구현은 한 기능씩 비교하여 효과를 분리한다.

## 3. 사용자 명령에서 완료까지의 목표 흐름

1. **명령 접수:** 사용자 요청·활성 제약·완료 기준·현재 경로·작업 ID를 확정한다.
2. **기억 선택:** 권한/범위/유효 상태를 먼저 거르고, 필수 지침과 관련 최신 사실·근거를 구분한다.
3. **입력 조합:** 안정적인 지침 부분, 작업 상태, 관련 근거, 현재 명령을 명확히 구분한다. 최종 전송 경로별로 구성 내역을 기록한다.
4. **조사·실행:** 검색 결과/파일/로그의 필요한 범위부터 읽는다. 전체 원본은 참조로 보존하고 필요하면 확장 조회한다.
5. **수정·검증:** 변경된 대상과 완료 기준에 맞는 검사를 수행한다. 같은 조건의 이미 완료된 검사만 증거를 갖춰 재사용한다.
6. **실패 복구:** 형식 오류, 구현 오류, 도구 오류, 근거 부족을 구분하여 필요한 단계부터 복구한다.
7. **작업 종료:** 실제 결과·미완료·검증 근거를 기록하고, 재사용 가치가 있는 결정과 현재 사실만 장기기억으로 승격한다.

같은 논리적 작업 ID에 계획·검색·요약·구현·검증·실패·재시도·최종 정리를 묶는다. 압축으로 추가된 요약 호출과 원문 재조회도 비용에 포함한다.

## 4. 단계별 실행 계획

### S0. 기준선과 관측 경로 보완

산출물: 현재 P0 위의 제공자별 usage fixture, 프롬프트 구성 진단, 재현 가능한 평가 입력.

- 최종 입력의 종류별 문자 수와 가능한 경우 모델 토큰 추정치를 기록한다: 필수 지침, 작업, RAG, 인계, 도구 설명/결과. CLI 내부의 보이지 않는 영역은 `unknown`으로 둔다.
- 정확한 모델 tokenizer가 확인되면 해당 버전으로 세고, 그렇지 않으면 추정/문자 수를 명시한다. 한국어를 일률적으로 4자=1토큰으로 환산하지 않는다. 사전 추정과 실제 provider usage를 별도 필드로 둔다.
- 이번 Grok CLI 1.0.4에서 `usage`와 `end.usage`, `modelUsage`가 실제 나왔다. 첫 수집 요청은 total_tokens=547,104, input_tokens=172,826, cache_read_input_tokens=371,072, output_tokens=3,206을 보고했다. 이 fixture에서는 입력+캐시 읽기+출력=총량이다. reasoning=2,390은 출력에 다시 더하지 않는다.
- 그러나 AutoUsage는 Grok를 ACP로 실행한다. CLI의 `--output-format streaming-json` 출력과 ACP 알림은 같은 계약으로 단정할 수 없다. `XAiAcpExtension.ts`의 `agentResult`/prompt completion에서 동일 소비값이 전달되는지 먼저 검증하고, turn별 값인지 누계인지·취소 시 부분 사용량·재연결 중복을 테스트한다.
- `usage`와 `end.usage`를 둘 다 합산하지 않는다. schema/version, native request ID, source counter scope를 확정하기 전 Grok coverage는 partial/unavailable로 유지한다. CLI 자체 보고 금액은 구독 잔액이나 실제 결제 증거가 아니다.
- `promptUses`는 활용 횟수이며 정답률이 아니다. 선택 trace와 실제 전달 receipt를 구분한다. 미리보기 호출을 실제 AI 소비로 세지 않는다.

완료 기준: Codex/Claude 기존 합계 회귀 없음, Grok fixture의 취소·완료·중복·누락 사례 통과, 추정/관측/미보고가 화면에서 혼동되지 않음.

### S1. 장기기억을 관련성과 현재 상태로 선택

산출물: 기억 선택기, 버전/출처 관계, 선택 이유 trace와 작은 진단 화면.

- **필수:** 현재 명령과 적용 범위 내 활성 사용자 지침은 반드시 보존한다. 생성 요약·유사도 점수가 이를 제거할 수 없다.
- **선택:** long-term-memory, working/run memory, 외부 RAG는 작업·파일 경로·식별자 관련성으로 고른다. 관련도가 낮으면 0개도 정상이다. 넓은 프로젝트 목표는 짧은 기본 문맥으로 유지하고 상세 근거를 분리한다.
- 먼저 기존 FTS/한국어 분석을 활용한다. BM25 원점수는 질의마다 척도가 달라 고정 전역 임계값으로 쓰지 않는다. 범위·식별자 일치·term coverage·평가 질의로 선택 기준을 조정한다.
- 환경/프로젝트/폴더 범위는 **검색 전에** 제한한다. 본문 중복 제거도 허용 범위 안에서만 수행한다. 공용 기억은 명시적으로 공유된 항목만 사용한다.
- 제안 메타데이터: `canonicalId`, `revision`, `supersedes`, `validFrom`, `validTo`, `evidenceRefs`; 기존 `research.verification`과 상태를 재사용한다. 단순히 최근에 편집됐다는 이유로 이전 검증 사실을 덮지 않는다.
- 현재 결론은 짧게, 실험/이전 결론/원문은 별도 근거로 둔다. 과거 비교 요청은 이전 버전도 검색한다. 모순이 해결되지 않았으면 양쪽 근거와 미해결 상태를 전달한다.
- 자동 중복 처리는 content hash에 의한 동일 자료부터 시작한다. 의미가 비슷한 결정은 관계 후보로 제시하고, 사용자 제약을 자동 합치거나 삭제하지 않는다.
- 결정 trace: 항목/청크 ID, revision, 선택·제외 이유, 문자/추정 토큰, current/history, 출처 검증 상태, 원문 참조. 본문 전체를 trace에 복제하지 않는다.

완료 기준: “웹 버튼 간격 수정”에 허브 세부 기록 0개, 허브 최신 성능 질의에 최신 결론과 실제 측정 근거 포함, 과거/현재 비교 질의에 필요한 양쪽 근거 포함, 필수 지침 누락·프로젝트 경계 침범 0건.

### S2. 형식 복구와 재시도 범위 축소

산출물: 형식 복구용 경로와 기존 실패 분류 연결. S1과 독립적으로 작게 적용 가능하다.

- `workspaceCollaboration.ts`의 형식 오류 시 전체 재작업 지시를 제거하고, 원래 산출물+schema 오류+요구 형식만 전달한다.
- 결정적으로 수정 가능한 포맷만 parser에서 복구한다. 누락된 사실·판정은 만들어 넣지 않는다. 단순 포맷 복구 실패는 기존 복구/사용자 결정 경로를 유지한다.
- 실패 종류별 입력은 `실패한 단계 / 정확한 오류 / 바뀐 조건 / 필요한 근거 / 허용된 재시도 범위`다. 이미 완료된 구현·검색·노드 결과를 유지한다.
- 가능한 CLI만 native 도구 권한으로 형식 복구의 쓰기를 제한한다. 프롬프트만으로 쓰기가 차단되었다고 보고하지 않는다. 사용자/제공자 정책 거부는 자동 우회하지 않는다.
- 형식 복구도 별도 시도/phase로 P0에 기록하되, 실패 비용을 없애거나 누적 사용량을 환불하지 않는다.

완료 기준: 잘못된 JSON/태그/필수 필드 테스트에서 본 작업의 검색·빌드·수정 재실행 0회. 실제 구현 실패는 필요한 수정·검증을 수행하고 시도 상한을 보존한다.

### S3. 단계별 문맥 예산·도구 결과·캐시 정렬

산출물: 최종 입력 조합 정책, 원문 참조 조회, provider capability 표.

- 현재 `maxContextChars`는 RAG 부가 문맥 한도이며 전체 CLI 컨텍스트 한도가 아니다. 사용자의 모델 한도와 최종 입력 경로를 확인하여 출력/추론/도구 응답 여유를 따로 확보한다.
- 선택형 메모리부터 줄이고 문단·청크 경계를 지킨다. 필수 제약이 넘치면 조용히 자르지 않고 크기와 이유를 표시하여 충분한 입력 경로/기존 경로로 처리한다. 작업 중단을 절감 성공으로 세지 않는다.
- 일반 채팅, 협업 계획/노드, 사고 대응, 모델 전환 인계의 적용 여부를 명시한다. 중복 주입 방지용 `contextRevision`/출처 ID를 사용한다. 일반 채팅에 새 자동 RAG를 연결할 때는 설정과 호환 경로를 설계하고, 저장만으로 모든 열린 CLI에 자동 주입된다고 주장하지 않는다.
- 검색은 제목·경로·짧은 관련 구간을 먼저 반환하고, 필요한 결과의 본문을 조회한다. 파일은 내용 hash+구간, 로그는 핵심 오류+검사 결과+원문 참조를 반환한다. 테스트 성공 로그를 매번 통째로 복제하지 않는다.
- 동일 조회 캐시는 environment/project/권한/질의/파일 hash 또는 corpus revision을 키에 포함한다. 파일 수정·기억 갱신 시 무효화한다. 실시간 상태와 쓰기 작업에는 무분별한 캐시를 적용하지 않는다.
- T3가 제공하는 도구부터 검색형 목록/페이지/범위 응답을 적용한다. CLI가 소유한 native 도구와 MCP schema는 해당 CLI의 지원 기능 안에서만 조정한다.
- 공통 지침·안정적인 도구 정의는 앞부분에 고정하고, 변하는 작업 내용·RAG·시각/실행 ID는 뒤쪽에 둔다. 선택 결과의 순서와 버전을 안정화한다. 캐시를 위해 낡은 사실을 유지하거나 무관한 내용을 추가하지 않는다.
- provider API의 cache-control/compaction/tool-search 옵션을 CLI 공통 옵션으로 노출하지 않는다. 지원 여부와 실제 native 이벤트를 확인한 기능만 adapter 경계에 연결한다. native compaction의 opaque 항목은 provider 간 공통 RAG 문서로 변환하지 않는다.

완료 기준: 필요한 원문 재조회 가능, 수정 뒤 낡은 캐시 사용 0건, 필수 지침 원문 보존, 실제 사용량과 cache read/write 및 완료 시간 별도 비교. 프롬프트가 짧아졌다는 사실만으로 비용 절감을 확정하지 않는다.

### S4. 협업 인계·검증 결과의 재사용

산출물: 근거를 가리키는 작업 인계와 종료 라운드 문맥. 기존 P1의 사용자 선택·원문 보존 원칙을 확장한다.

- 의존 결과는 `결론 / 변경물 / 검사·결과 / 미완료 / 실패 / 근거 ID+revision`을 전달한다. 모든 선행 노드 결과를 넣지 않고 기존 직접 의존성 규칙을 유지한다.
- 회의는 완료 라운드의 합의·반대·미해결과 현재 라운드 원문을 사용한다. 사용자 개입과 답변은 별도 필수 영역에 보존한다. 현재 코드는 의장 정리와 원 발언을 함께 전달하므로 정리의 중복 감소 효과를 측정한다.
- 가능하면 이미 작성한 결과/의장 정리를 재사용한다. 모든 턴마다 별도 요약 모델을 호출하지 않는다. 요약이 불완전하거나 근거 접근이 실패하면 원문으로 돌아간다.
- 검증 재사용 키에는 요구사항 버전, diff/관련 파일/lockfile hash, 명령·도구 버전·환경, 결과·로그 참조를 포함한다. 의존성 범위가 불명확하면 보수적으로 무효화한다.
- 외부 서비스/비결정적 상태 검사는 새로 확인한다. 독립 검증이 필요한 변경은 유지하며, 참가자나 요청된 검증을 비용만으로 줄이지 않는다.

완료 기준: 오래된 사용자 수정·미완료·반대 의견을 잃지 않음, 원문 재현 가능, 조건 변화 시 재검증, 요약·재조회까지 포함한 완료 작업당 사용량 감소 확인.

### S5. 검색 누락이 남을 때 하이브리드 검색 추가

산출물: 기존 FTS와 비교 가능한 선택형 벡터 검색/재순위 경로.

- 평가에서 동의어·의미 질의 누락을 확인한 뒤 BM25 후보와 벡터 후보를 합친다. RRF 등 순위 결합 후 중복 제거하고 제한된 후보만 재순위한다.
- 문서 제목·프로젝트·시점·현재/과거 구분 등 확정된 메타데이터를 청크에 붙인다. 매 청크마다 비싼 LLM 맥락 생성이 필요한지는 별도 실험한다.
- 기존 항목당 1청크 제한을 무작정 풀지 않는다. 같은 문서에서 필요한 서로 다른 근거 청크 2개 이상을 선택할 수 있도록 청크 ID를 추가하고, 중복 구간/부모 문맥을 관리한다.
- 임베딩은 content hash+모델/차원/청크 버전으로 증분 생성한다. 원본·FTS가 기준 저장소이며 벡터 색인은 재구축 가능해야 한다. 재색인 중에는 기존 FTS 경로를 유지하고 색인 revision을 원자적으로 전환한다.
- 로컬 임베딩/재순위와 외부 서비스의 정확도·메모리·지연·운영 비용을 비교한 뒤 선정한다. 현재 72개 활성 항목만을 근거로 별도 벡터 서버나 native rewrite를 도입하지 않는다.

완료 기준: 식별자·오류 코드 검색 품질 유지, 의미 질의의 Recall@k/nDCG와 최종 답의 근거 정확도 개선, 색인 갱신/삭제 반영, 지연·메모리·임베딩 비용 포함한 이점 확인.

## 5. 평가와 도입 조건

첫 평가 집합은 프로젝트 자료에서 **40개 질의**를 구성한다: 직접 사실 8, 한국어 동의어 8, 최신/과거/모순 8, 무관 작업 8, 범위·사용자 제약 8. 기대 항목/청크와 금지 항목을 사람이 검토하여 고정한다. 이 숫자는 평가 설계이며 실행 완료 건수가 아니다.

실작업은 문서 수정·작은 구현·리팩토링·버그 수정·협업 검증 5종을 동일 모델/추론/CLI 버전/코드 기준/완료 기준으로 기존과 개선 각각 최소 3회 비교한다. 이는 파일럿이며 통계적 유의성을 보장하지 않는다. 작업 트리를 격리하고 실행 순서를 섞으며 캐시가 유지된 경우와 새 세션을 나눠 본다.

| 지표           | 판정 방법                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------- |
| 작업 전체 토큰 | 제공자별 정규화된 입력(캐시 포함)+출력(추론 포함). 하위 작업/실패/재시도/요약도 포함하고 중복 관측 제거 |
| 완료당 비용    | 해당 실험군 모든 시도 사용량 ÷ 동일 완료 기준을 통과한 작업 수. 실패 비용을 성공 표본에서 숨기지 않음   |
| 부분 계측      | complete 집합의 주 비교와 partial/unavailable를 별도 제시. 미보고를 0으로 채우지 않음                   |
| 캐시           | cache read/write, 입력 비율, 지연을 분리. 실제 금액/구독 한도 감소와 토큰 감소를 동일시하지 않음        |
| 품질           | 완료 기준, 테스트, 필수 제약, 최신 근거, 결함·재작업·실패율. 품질 저하를 작은 토큰 수로 상쇄하지 않음   |
| RAG            | 무관 주입, 필수 근거 누락, 최신/과거 판정, 범위 위반, 선택 이유 추적                                    |
| 운영           | 검색/조합 및 전체 완료 시간 p50/p95, 메모리, 색인 생성/갱신 시간. 충분한 표본에서만 백분위 해석         |

고정 절감률은 아직 없다. 파일럿에서 품질·완료율을 유지하면서 실제 총사용량 감소가 반복 확인된 기능만 기본 적용 후보로 삼는다. 기능별 설정·이전 조합 경로를 유지하고 되돌릴 때 원문/이벤트/사용량 원장은 삭제하지 않는다.

계약 변경은 `packages/contracts`에서 시작해 서버·client-runtime·웹·데스크톱·모바일·원격 연결까지 전달한다. 제공자별로 Codex, Claude/Fable, Grok, Cursor, OpenCode, Gemini의 지원/미지원/미관측을 표시한다. 집중 테스트·범위 타입 검사만 수행하고 저장소 전체 검사는 요청하지 않는다. 실제 클라이언트 검증은 별도 실행 단계에서 사용자의 브라우저/컴퓨터 사용 승인 범위에 따른다.

## 7. 장기기억 보존 방식

AutoUsage 프로젝트에 짧은 장기기억 1개와 상세 RAG 자료를 분리하여 저장한다. 전체 보고서를 장기기억 본문에 반복해서 붙이지 않는다. 상세 계획, 공식 근거/수집 방법, Grok 원보고서, 검색·호출 증거는 서로 연결하되 verified/unverified를 구분한다.

실제 저장은 `project.knowledge.item.upsert` 명령을 사용한다. 운영 SQLite를 직접 수정하지 않는다. 저장 후 본문 일치, FTS 재검색, `composeWorkspacePrompt.sourceReferences`의 실제 선택을 확인한다. 저장 및 미리보기 성공은 열린 AI 세션의 자동 재로딩이나 실제 작업 성능 개선 완료를 뜻하지 않는다.
