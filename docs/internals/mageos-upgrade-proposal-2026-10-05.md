# CryptoMage 가이드 기반 NewAutoUsage 업그레이드 제안

작성일: 2026년 10월 5일 KST  
대상: 현재 T3 Code 기반 NewAutoUsage의 웹 데스크톱 모바일 클라이언트와 서버  
조사 자료: [CryptoMage AI 코인 올인원 가이드](https://cryptomage-mageos.pages.dev/guide/)

## 1 우선 권고

다음 업그레이드는 **실제 산출물로 작업 상태를 판정하고, 정지 사유를 재시작 경로 전체에 보존하며, 백업의 복구 가능성을 확인하는 기능**부터 진행하는 것이 좋다. 현재 프로그램에는 MCP, 스킬과 플러그인, 다중 AI 협업, 작업 대시보드, 자동 검증, RAG, 예약 실행이 이미 있다. 이 기능들을 연결해 장시간 운영 중의 실패를 빨리 발견하고 재현할 수 있게 만드는 개선의 가치가 크다.

첫 개발 묶음은 아래 U1 U2 U3으로 구성한 **운영 상태 개선**, 다음 묶음은 U4 **백업과 복구 검증**을 권장한다. RAG 의미 검색은 기존 실험에서 운영 채택을 보류한 이력이 있으므로 새 평가에서 효과가 확인될 때 추가한다. 코인 리서치와 외부 알림은 선택 기능으로 분리한다.

이 문서는 조사와 개발 제안이다. 프로그램 코드 수정, 도구 설치, 계정 연결, 운영 데이터 변경, 실행 중인 프로그램 교체는 이번 작업에 포함하지 않았다. 아래의 공수와 목표 수치는 제안이며 측정 결과나 확정 일정이 아니다.

## 2 가이드에서 확인한 내용

링크는 AI 활용과 코인 리서치 및 봇 운영을 설명하는 교육 가이드다. 페이지에는 2026년 10월판이라는 표시와 9개 장의 본문이 있다. 본문 전체와 운영 실패 및 RAG 관련 인포그래픽 5개를 확인했다. 연결된 Mage OS 홈페이지의 기능이나 실제 봇 성능을 직접 시험한 것은 아니다.

## 4 개발 우선순위

P0는 운영 상태와 복구 신뢰성, P1은 작업 품질과 효율, P2는 선택 확장이다. 공수는 기존 구조를 재사용하는 개발자 1명의 구현과 집중 검증에 대한 초안이다. 외부 계정 심사, 앱 배포 심사, 새로운 서비스 운영 준비는 포함하지 않는다.

## 5 운영 상태 개선

### U1 실제 산출물과 진행 상태 관측

**문제와 근거.** HTTP 200이나 실행 중인 PID만으로는 예약 보고서, 자료 수집기, RAG 색인 작업이 실제로 진행되는지 알기 어렵다. 현재 프로그램 감시는 HTTP TCP와 시스템 지표를 이미 지원한다. 여기에 작업 결과의 최신성을 더한다. [가이드의 결과 없는 실행 사례](https://cryptomage-mageos.pages.dev/guide/#ch-08-zombie)에서 가져온 개선 방향이다.

**제안하는 동작.** 작업 카드에 마지막 정상 검사, 마지막 성공 산출물, 다음 결과 예정 시각을 표시한다. 결과는 검증 영수증, 저장된 문서나 색인의 revision, 승인된 외부 작업의 결과 확인처럼 작업별로 지정한다. AI 응답 완료, 검증 통과, 실제 적용 확인은 각각 표시한다. 서버 시작 요청은 포트 응답 등 등록된 확인 조건을 만족한 뒤 적용 확인으로 표시한다.

**최소 구현.** 기존 프로그램 및 작업 실행 ID에 `lastSuccessfulResultAt`, `expectedResultBy`, `resultEvidenceRef`에 해당하는 정보를 연결한다. 감시 지표에 마지막 성공 결과의 경과 시간을 추가하고, 기존 사고 기록과 대시보드에 투영한다. 모든 로그 줄을 웹소켓으로 보내지 않고 상태 전환과 요약 시각을 전달한다.

결과가 나와야 하는 작업에만 기준을 적용한다. 실행할 일이 없는 대기 상태, 예약 시각 이전, 사용자가 일시정지한 작업에는 결과 지연 경고를 만들지 않는다. 결과를 관측할 수 없으면 정상이나 실패로 추정하지 않고 관측 불가로 표시한다.

**완료 조건.** 정상 HTTP 응답을 유지하면서 결과 생성만 멈춘 fixture에서 지연을 감지한다. 대기 작업에서는 오탐하지 않는다. 재접속한 모바일에도 같은 마지막 결과 시각이 표시된다. 오래된 검증 결과가 새 변경의 적용 확인으로 재사용되지 않는다.

### U2 정지 사유와 재시작 정책 공유

**문제와 근거.** 현재 프로그램 실행, 감시 플레이북, 수정 후 재시작, 서버 시작 시 자동 실행은 서로 다른 진입 경로다. 가이드는 정지를 결정한 주체와 재시작 주체가 같은 이유를 공유해야 한다고 설명한다. 현재 앱에서 그 충돌이 발생했다고 확인한 것은 아니며, 각 경로에서 일관되게 적용할 영속 정책을 제안한다. [가이드의 재시작 충돌 사례](https://cryptomage-mageos.pages.dev/guide/#ch-08-watchdog)

**제안하는 동작.** 실행 실패, 사용자 정지, 유지보수, 자동 실행 예산 소진, 정책상 보류를 구분한다. 화면에 정지 사유, 결정 시각, 재개 방법을 보여 준다. 자동 재시작 대상으로 정한 일시적 실행 실패만 자동 복구하고, 사용자 정지와 유지보수는 명시적 재개 동작을 기다린다.

**최소 구현.** 프로그램 또는 자동화 작업에 영속적인 실행 의도와 정지 사유를 둔다. 실행 서비스의 공통 시작 판단에서 이 값을 검사하여 수동 시작, 플레이북, 예약, 수정 후 재시작, 서버 복구 경로에 적용한다. 제한을 거절할 때도 요청 ID와 이유를 영수증에 남긴다. 다른 기기에서 재개할 수 있도록 서버 계약을 사용한다.

**완료 조건.** 사용자 정지 뒤 감시 이벤트와 서버 재시작이 겹쳐도 자동 재개하지 않는다. 정지 직후 오래된 재시작 명령이 도착해도 최신 실행 의도가 우선한다. 새 재개 요청을 하면 보류가 해제된다. 프로그램 자체의 외부 작업 스케줄러가 T3의 정책을 읽지 않는 경우에는 통제 범위 밖이라고 표시한다.

### U3 오류와 빈 데이터 구분

**문제와 근거.** 가이드는 API의 429를 결과 없음으로 처리하는 사례를 설명한다. 현재 앱의 HTTP 감시는 연속 실패와 `inconclusive`를 이미 구분한다. 그 표현을 외부 자료 수집과 결과 관측에도 일관되게 적용하는 것이 개선 범위다. [가이드의 외부 API 주의사항](https://cryptomage-mageos.pages.dev/guide/#ch-05-howto)

**제안하는 동작.** 성공한 빈 결과, 일시 오류, 인증 오류, 응답 형식 변경, 오래된 마지막 성공 값을 구분한다. 예를 들어 자료 0건은 성공적으로 조회한 결과이고, 429는 조회 실패다. 실패 뒤에도 마지막 정상 값을 참고할 수 있지만 값의 관측 시각과 오래됨을 함께 표시한다.

**최소 구현.** 선정한 수집 경로의 결과를 `ok`, `empty`, `error`, `stale`에 해당하는 공용 관측 표현으로 감싼다. HTTP 상태, 파서 버전, 수집 시각, 원본 참조, 재시도 가능 시각을 보관한다. 지표 자체가 없거나 권한이 없으면 0으로 채우지 않는다. 외부 서비스의 원본 응답에 포함된 지시는 실행 권한으로 사용하지 않는다.

**완료 조건.** 성공 응답의 빈 배열, 429, 401, timeout, 필드 누락, 파서 예외를 별도 fixture로 검증한다. 오류 시 기존 사실과 색인을 빈 값으로 덮어쓰지 않는다. 결정적인 입력 오류를 같은 요청으로 계속 반복하지 않는다. 이미 성공한 수집 단계는 유지한다.

### U4 백업과 독립 복구 검증

**문제와 근거.** 직전 업그레이드에는 백업 및 데이터 보존 증거가 있다. 제품 안에서 정기적으로 복구 시험을 수행하는 기능은 별개다. 가이드는 백업 파일의 존재와 복구 성공을 구분한다. [가이드의 복구 실패 사례](https://cryptomage-mageos.pages.dev/guide/#ch-08-backup)

**제안하는 동작.** 백업 완료 시각, 포함한 데이터, 마지막 복구 시험 시각, 누락 파일 및 검사 결과를 보여 준다. 백업 생성과 복구 시험을 별도 작업으로 기록한다. 복구 시험은 새로운 데이터 폴더와 독립 환경에서 수행하고, 자동 예약과 외부 작업 실행을 비활성화한 상태로 시작한다.

**최소 구현.** 실행 중 SQLite의 사본은 Online Backup API 또는 `VACUUM INTO`로 만들고 원본 DB는 수정하지 않는다. 두 방식은 SQLite가 문서화한 온라인 백업 경로다. [SQLite Backup API](https://www.sqlite.org/backup.html), [VACUUM INTO](https://www.sqlite.org/lang_vacuum.html#vacuum_with_an_into_clause)

DB, 설정, 첨부 파일, 디자인 이미지, 보관한 CLI 원본, 장기기억 파일 및 설치 영수증의 범위와 해시를 manifest에 기록한다. DB와 첨부 파일은 하나의 파일 시스템 트랜잭션이 아니므로 스냅샷 시점의 참조 목록을 고정하고 대상 파일의 존재와 해시를 확인한다. 누락된 파일이 있으면 완전한 백업으로 판정하지 않는다. 검색 색인은 필요하면 원본에서 다시 만들 수 있도록 복구 절차를 분리한다.

자격 증명은 일반 자료의 문자열 제거 규칙으로 처리하지 않는다. 제외하는 비밀은 종류와 재인증 필요 여부를 명시하고, 필요한 암호화 백업의 복호화 수단을 별도로 시험한다. 공개 식별자나 일반 문서를 비밀로 오인해 지우지 않는다. desktop profile의 쿠키나 로그인을 다른 PC에서도 사용할 수 있다고 보장하지 않는다.

**완료 조건.** 독립 폴더에서 DB 무결성, 원본 ID 및 본문 보존, 첨부 참조, 기억 재검색, 설정 로딩을 확인한다. 재인증이 필요한 항목은 실패나 성공으로 숨기지 않고 목록으로 남긴다. 중단된 백업, 누락 이미지, 부족한 디스크와 이전 schema의 복구를 집중 검증한다. 복구 시험 결과가 실제 확인한 범위를 명시해야 한다.

## 6 작업 품질과 효율 개선

### U5 조건부 하이브리드 RAG

**제안.** 먼저 현재 자료의 새로운 평가 집합으로 FTS 검색 누락을 확인한다. 의미가 같은 표현을 놓치는 사례가 남아 있을 때 FTS 후보와 임베딩 후보를 함께 가져와 RRF로 순위를 합친다. 선택된 결과에도 현재성 검증 상태 프로젝트 및 폴더 범위 필터를 유지한다. 기존 관련 기억 선택을 교체하지 않는다.

가이드에 소개된 bge-m3는 비교 후보로 삼을 수 있다. 공식 모델 자료에는 다국어 및 1024차원 지원이 명시돼 있다. 이것만으로 이 PC의 최적 모델이나 검색 개선이 입증되는 것은 아니다. [BAAI bge-m3 모델 자료](https://huggingface.co/BAAI/bge-m3)

**최소 구현.** 내용 해시, 청크 규칙, 모델 ID 및 차원을 키로 증분 임베딩을 생성한다. 질의와 문서는 같은 임베딩 규칙을 사용한다. 별도 상시 벡터 서버부터 도입하지 않고 기존 서버의 선택 기능과 소규모 색인으로 평가한다. 생성 작업의 동시 실행과 메모리를 제한하고 색인 장애 시 FTS로 검색한다. 재색인 완료 뒤 revision을 전환한다. 기존 FTS의 BM25 기능을 유지한다. [SQLite FTS5](https://sqlite.org/fts5.html)

**채택 조건.** 기존 평가에 사용하지 않은 새 질의와 검토한 정답 근거로 Recall at k와 nDCG 및 최종 답변의 근거를 비교한다. 식별자, 함수 이름, 오류 코드의 정확한 검색을 유지하고 의미 질의의 누락을 줄여야 한다. 프로젝트 경계 위반은 허용하지 않는다. p95 검색 시간, 메모리, 최초 및 증분 색인 시간도 함께 기록한다. 이점이 확인되지 않으면 FTS를 유지한다. 재순위기는 RRF만으로 해결하지 못하는 사례가 남을 때 별도 비교한다.

### U6 외부 Markdown 노트 증분 수집

**제안.** Obsidian 볼트나 사용자가 지정한 Markdown 폴더를 읽기 원본으로 등록한다. 바뀐 문서만 후보 자료로 가져오고 검색 색인을 갱신한다. 기존 프로그램이 생성하는 장기기억 Markdown 사본과 외부 노트 수집을 구분한다. [가이드의 파일 기억과 증분 갱신](https://cryptomage-mageos.pages.dev/guide/#ch-02-mykb)

**최소 구현.** 원본 ID, 상대 경로, 내용 해시, 수집 시각 및 source revision을 기록한다. 외부 노트는 파일이 원본이고 프로그램의 항목은 수집 사본이다. 프로그램에서 관리하는 기억은 기존 event log와 데이터가 원본이며 Markdown 파일은 사본이다. 양방향 자동 동기화는 초기 범위에서 제외한다. 파일 변경 이벤트는 묶어 처리하고 주기적인 해시 대조로 놓친 변경을 발견한다.

자동 요약이 필요하면 원본과 요약을 별도로 보존하고 사실, 추정, 미확인을 구분한다. 외부 문서가 바뀌거나 삭제되면 해당 revision의 검색 자료를 갱신하되 사용자가 별도로 작성한 기억은 삭제하지 않는다. 외부 자료를 사용자 지침이나 활성 장기기억으로 자동 승격하지 않는다.

**완료 조건.** 파일 수정, 이름 변경, 삭제, 중복 내용, 한글 경로, 프로그램 재시작 후 변경 누락을 검증한다. 새 수집본의 내용 해시와 원문이 일치해야 한다. 끄기와 원본 연결 해제를 제공하고, 이전 사본을 보관할지 삭제할지 범위를 명확히 보여 준다. 외부 폴더에 프로그램이 쓰지 않아야 한다.

### U7 독립 검증 작업 템플릿

**제안.** 기존 역할과 task graph를 사용하여 리서치, 구현, 검증의 작업 지시를 미리 채우는 템플릿을 제공한다. 각 작업은 목표, 사용자 제약, 변경 범위, 요구 산출물, 실제 검사 및 원문 근거를 포함한다. 독립 검증이 필요한 변경에서 구현자와 다른 검증자를 지정하기 쉽게 한다. [가이드의 역할 분담](https://cryptomage-mageos.pages.dev/guide/#ch-03-team), [별도 AI 검증](https://cryptomage-mageos.pages.dev/guide/#ch-03-redteam)

**최소 구현.** 새 에이전트 엔진을 만들지 않고 기존 coordinator implementer reviewer verifier binding과 validation 영수증을 조합한다. Claude를 구현, Codex를 검증, Grok를 최신 자료 조사로 선택하는 예시는 제공할 수 있지만 역할은 사용자가 바꿀 수 있어야 한다. 공급자의 우수성을 일반화해 고정하지 않는다.

검증 대상의 요구사항 revision, worktree 및 diff 해시, 명령과 결과를 연결한다. 검사 대상이 바뀌면 이전 통과 표시를 현재 결과로 쓰지 않는다. 이미 존재하는 쓰기 체인 격리와 직렬화를 그대로 사용한다. 읽기 전용 검증이 기술적으로 지원되는 공급자에서만 그 제한을 보장한다.

**완료 조건.** 검증자가 실제 변경물을 읽고, 준비된 결함 fixture에서 실패를 재현한다. AI의 문장만으로 테스트 통과를 판정하지 않는다. 다른 검증자가 실행되지 못했을 때 독립 검증 완료로 표시하지 않는다. 단순 문서나 낮은 영향의 작업에 추가 AI 호출을 일괄 강제하지 않는다.

### U8 자동 작업 예산과 요청 대기열

**제안.** 기존 사용량 원장과 계정 한도를 바탕으로 프로젝트 자동 작업의 실행 횟수, 동시 실행, 관측한 토큰 및 선택적 비용 예산을 관리한다. 감시의 시간별 및 일별 자동 턴 예산과 예약 실행의 일부 backoff를 재사용한다. [가이드의 비용과 요청 제한](https://cryptomage-mageos.pages.dev/guide/#ch-01-cost)

**최소 구현.** 새로운 자동 실행 전 공유 예산을 확인하고 이미 시작할 작업의 예약량을 고려한다. 429와 서비스별 retry 시각은 공급자 인스턴스 또는 해당 키의 범위에서 공유한다. 큐에서 취소, 재개, 보류 사유 확인이 가능해야 한다. 서버가 재시작돼도 보류 시각과 정지 사유가 사라지지 않는다. 이미 실행한 비용이나 실패한 시도의 사용량은 원장에서 차감하지 않는다.

구독 CLI 토큰 수와 API 청구액은 별도 값이다. 가격 또는 실제 비용이 없는 공급자를 0원으로 집계하지 않는다. 설치된 CLI가 모든 native 요청을 노출하거나 즉시 중단할 수 있는 것은 아니므로 초기 예산은 **새 자동 작업 시작 제한**으로 정의한다. 실행 중 소비량의 정확한 금액 상한을 보장하는 기능으로 홍보하지 않는다. 예산 때문에 사용자 선택 모델을 임의로 낮추지 않는다.

**완료 조건.** 같은 계정의 여러 프로젝트가 동시 시작할 때 한도를 초과하는 새 실행을 보류한다. 미보고 사용량과 확정된 사용량을 구분한다. 재시작 후에도 요청 제한의 대기 시간이 유지된다. 사용자가 예산을 바꾸거나 자동화를 끄면 큐 상태가 일관되게 반영된다.

## 7 선택 확장

### U9 출처 기반 리서치와 선택 알림

**제안.** 관심 주제의 공식 공지, 웹 문서, 허용한 공개 채널 자료를 수집하여 이전 내용과 비교하는 리서치 템플릿을 추가한다. 첫 버전은 일반 개발 문서와 서비스 공지에도 쓸 수 있는 구조로 만든다. 코인 기능을 선택하면 체인과 계약 주소로 대상을 식별하고 자료의 수집 시각을 함께 표시한다.

현재 연구 자료에는 문서 단위 출처와 검증 상태가 있으므로, 개별 주장에 `fact`, `inference`, `unverified`와 근거 참조를 추가하는 것이 차이다. 공식 문서의 주장과 실제로 재현한 결과도 구분한다. URL이 있다는 이유만으로 verified로 처리하지 않는다. 외부 사이트 변경이나 문서 갱신은 후보 자료로 저장하고, 비교 및 확인 뒤 현재 자료에 반영한다.

코인 리서치의 선택적 조회 소스로는 [DexScreener API](https://docs.dexscreener.com/api/reference)와 [GoPlus API](https://docs.gopluslabs.io/reference/api-overview)를 검토할 수 있다. 공식 문서에서 API와 토큰 보안 조회 기능의 존재를 확인했다. 실제 키 발급, 전체 지표의 가용성, 현재 사용 조건 및 품질은 개발 착수 시 각각 확인해야 한다. 유료 서비스와 가이드의 추천 링크는 자동 연결하지 않는다.

알림을 켜는 경우 완료, 실패, 사용자 입력 필요 상태를 요약해서 보낸다. 동일 사건 ID와 상태 전환 기준으로 중복을 억제하고 마지막 전송 성공 결과를 남긴다. 외부 전송은 사용자가 지정한 목적지와 범위에 한정하며 기본값은 꺼짐이다. 재시작 후 미전송 항목을 다시 확인할 수 있게 한다.

**완료 조건.** 서로 같은 이름의 다른 대상을 혼동하지 않는다. 429나 누락 필드를 정상적인 0건으로 처리하지 않는다. 주장의 원문과 시각을 열어 볼 수 있다. 알림의 실패와 재전송을 확인할 수 있고 외부 서비스가 제공하지 않는 exactly once 보장은 주장하지 않는다. 초기 범위는 조회와 보고이며 주문 서명 및 자금 이동은 포함하지 않는다.

### U10 확장 업데이트 변경 내용 확인

**제안.** 현재 MCP와 스킬 및 플러그인의 출처 표시를 확장하여 업데이트 전후에 추가된 도구, 변경된 실행 명령, 새로운 훅 및 환경 변수 이름을 보여 준다. 설치 결과와 이전 버전을 기록하여 실패한 업데이트를 확인하고 지원되는 경우 되돌릴 수 있게 한다. [가이드의 확장 설치 검토](https://cryptomage-mageos.pages.dev/guide/#ch-07-agent)

**최소 구현.** 현재 관리형 도구의 고정 버전과 설치 영수증을 재사용한다. native CLI가 업데이트나 복원을 지원하는지 확인한 작업만 표시한다. 로컬 스킬의 내용 해시와 이전 사본을 비교하고 프로그램이 소유한 설치에 한해 복원을 제공한다. 도구 설명으로 알 수 있는 기능과 기술적으로 제한할 수 있는 권한을 구분한다. 환경 변수의 값은 변경 설명에 노출하지 않는다.

**완료 조건.** 도구 목록에 없는 실행 훅의 변경도 확인할 수 있어야 한다. 검사할 수 없는 형식은 확인 불가로 표시한다. 사용자의 기존 외부 설치를 프로그램 소유 설치로 취급하지 않는다. 체크섬은 파일 동일성 확인이며 출처의 신뢰성이나 모든 악성 동작 부재를 보증한다고 설명하지 않는다.

## 8 UI와 공통 적용 방식

가이드의 목차, 짧은 요약, 용어 설명 방식은 기존 제어센터의 탐색에 활용할 수 있다. 메뉴마다 요약과 현재 상태를 먼저 보여 주고 세부 설정 및 증거를 펼쳐 보도록 한다. 기능이 많은 상황에서 사용자가 다음에 할 일을 쉽게 찾는 것이 목적이다.

| 화면          | 추가할 정보                                      | 연결할 사용자 동작                |
| ------------- | ------------------------------------------------ | --------------------------------- |
| 작업 대시보드 | 마지막 산출물 시각, 결과 지연, 검증 및 적용 확인 | 결과 열기, 실패 근거 확인         |
| 프로그램 관리 | 생존 상태와 업무 상태, 정지 사유, 재시작 제한    | 정지, 명시적 재개, 감시 기준 변경 |
| 자동화 관리   | 다음 실행, 보류 이유, 요청 대기 시간, 예산       | 끄기, 취소, 예산 변경 및 재개     |
| 자료 관리     | 원본 경로, 수집 시각, revision, 검색 방식과 상태 | 원문 열기, 재수집, 연결 해제      |
| 백업 관리     | 백업 범위, 파일 누락, 복구 시험 시각과 결과      | 백업 생성, 독립 복구 시험         |
| 확장 관리     | 설치 출처, 버전, 도구와 훅의 변경                | 업데이트, 끄기, 지원되는 복원     |

**클라이언트.** 웹과 데스크톱은 같은 UI와 서버 계약을 사용한다. 모바일에서는 같은 상태와 핵심 제어를 제공하고, 긴 로그나 세부 비교는 필요한 때 조회한다. 서버 로컬 경로를 모바일에서 바로 열 수 있다고 가정하지 않고 인증된 원문 조회를 사용한다. 진입점은 채팅, 설정, 제어센터, 명령 팔레트, 기존 키바인딩의 적용 여부를 함께 확인한다.

**공급자.** 작업 관측과 백업은 서버 기능이므로 공통 적용한다. Codex Claude Grok의 native 도구, 읽기 전용 실행, 사용량 보고 차이는 adapter에서 처리한다. Cursor와 OpenCode에도 공통 상태는 보여 주되 native 검증 제한, 확장 관리, 상세 사용량은 각 adapter의 실제 지원을 확인한다. 미지원 기능을 공통 옵션으로 작동한다고 표시하지 않는다.

**원격 연결.** 모든 제어와 자료 조회는 연결한 environment의 RPC와 인증을 사용한다. 환경 및 프로젝트 경계를 포함한 식별자로 관측, 큐, 원본 참조를 저장한다. localhost 주소를 클라이언트 번들에 고정하지 않는다. 다중 기기의 중복 클릭은 같은 요청이나 사건으로 처리하고 서버가 결과를 확정한다.

**성능.** 상태 변화의 영수증과 요약을 전송하고 필요한 증거만 조회한다. 전체 대화와 로그를 주기적으로 다시 보내지 않는다. 화면에 상시 움직이는 티커, 배경 캔버스, 점멸 상태를 추가하지 않는다. 임베딩과 백업 작업의 동시 실행 및 메모리 사용은 제한한다.

## 9 개발 순서와 검증 계획

### 첫 단계 운영 상태와 복구

U3의 관측 표현을 좁은 경로에 먼저 적용하고 U1 U2를 연결한다. U4는 독립된 작업으로 추가한다. 기능 4개의 공수 합계는 10일에서 18일이며 통합과 교체 검증에 2일에서 4일을 더 잡으면 약 12일에서 22일이다. 이는 구현 경로가 확정되기 전의 추정이며 네 기능을 한 번에 교체해야 한다는 뜻은 아니다.

첫 단계는 다음 조건을 만족할 때 끝낸다.

- 프로세스는 살아 있지만 결과가 멈춘 fixture를 감지하고 정상 대기에서 오탐하지 않는다.
- 사용자 정지와 유지보수 상태를 모든 앱 소유 시작 경로 및 서버 복구 뒤에도 보존한다.
- 오류, 빈 결과, 오래된 관측을 구분하여 기존 자료를 잘못 덮어쓰지 않는다.
- 독립된 데이터 폴더의 복구 시험이 원본 기록과 첨부 참조를 확인한다.
- 웹 데스크톱 모바일에 동일한 서버 판정과 재개 가능 상태를 전달한다.

### 다음 단계 필요한 품질 개선 선택

사용 패턴에 따라 U6 U7 U8 중 필요한 것부터 선택한다. 외부 노트가 많으면 U6, 구현과 검증의 반복 작업이 많으면 U7, 밤새 예약 및 감시를 돌리면 U8의 효과가 크다. U5는 새로운 평가에서 현재 검색이 놓치는 자료가 확인된 뒤 착수한다. 기존 RAG 설정과 되돌리기 경로를 유지한다.

### 마지막 단계 선택 리서치와 확장 관리

U9는 사용자가 정한 출처, 계정, 주제와 알림 목적지를 확정한 뒤 개발한다. U10은 확장 업데이트가 잦거나 변경 내용을 확인하기 어려울 때 추가한다. 두 항목은 기본 운영 개선의 완료 조건을 늘리지 않는다.

### 구현 검증과 교체 원칙

승인된 개발을 시작할 때 기존 프로그램과 별도 작업 공간에서 구현하고, 복사한 일관된 데이터 스냅샷으로 집중 검증한다. 코드 변경 범위에 맞는 계약 서버 및 클라이언트 타입 검사와 테스트를 수행한다. 저장소 전체 검사는 이 제안의 기본 절차에 넣지 않는다.

서버 테스트는 typed receipt와 worker drain을 기준으로 판정하고 잠깐 기다렸다는 이유로 성공을 추정하지 않는다. UI의 실제 조작 검증이 필요한 단계에서는 이 프로젝트 규칙에 따라 사용자의 브라우저 또는 컴퓨터 사용 동의를 받은 뒤 한 번 통합 확인한다.

교체 작업이 승인된 경우에는 정확한 실행기, 데이터 위치, 프로세스 신원과 로그를 확보한다. 기능별 설정을 되돌릴 수 있게 만들고 source 변경과 데이터 migration을 구분한다. 웹 및 백엔드 응답과 데스크톱 실행을 각각 확인한다. 실패 시 어느 단계가 실패했는지와 유지되는 원본 및 복구 경로를 기록한다. 이번 조사에서는 이 교체 절차를 실행하지 않았다.
