# Task condition review and mandatory user directives

The web composer and desktop wrapper expose two per-folder toggles: ask-first and conditions. Pressing an enabled toggle turns it off; enabling the other switches modes. Both off means direct submission, which is the default for a folder without a saved preference. There is no separate direct-execution control. The existing persisted form toggle migrates to conditions/direct without replacing an explicit choice. Ask-first restores provider instructions to explain the plan, ask the necessary questions through supported tools, and wait for an answer; simple questions still receive a direct prose answer. Normal turns, Owner input and plan follow-ups include these instructions, while meetings use their existing askFirst flag. Selecting ask-first does not open the conditions form. Stop commands and native pending question answers keep their original paths.

Conditions mode reviews a new task before dispatch. Opening or cancelling the dialog does not send a provider request. Ongoing meeting participation retains its existing submission path. Plan approval buttons remain separate explicit approvals. Mobile does not yet render these toggles or the form; the new wire fields are optional for compatibility. Question tools and enforcement depend on the selected provider; the mode does not change the thread's native permissions.

`ApprovedTaskConditions` carries the reviewed fields and explicit action choices. New normal chat sends set `requireTaskConditions`; the normalizer rejects a missing or stale approval before writing attachments, and the decider repeats validation before producing events. The server renders the approved conditions into the durable user message. Inspection turns override the requested runtime and interaction mode without changing the thread's defaults. The provider reactor uses the event's runtime mode when creating or reusing a native session; the next turn restores the thread's chosen mode.

This is a task review feature, not a trust boundary against another client. Clients can still submit ordinary turns without requiring task conditions. Textual exclusions are instructions to the provider; native sandbox and plan behavior depend on each adapter. Managed collaboration, Owner input and plan execution accept the reviewed text but do not offer an inspection-only choice.

Explicit active user directives in project scope apply to their project; explicit environment-scope directives apply across the environment. `WorkspaceMemory.context` reads these authoritative records independently of retrieval relevance and automatic history settings. Automated turns request directives only and do not acquire historical context through this path. Agent-authored material, archived directives, folder directives and other projects' private records do not become global instructions. This also makes newly created projects receive the user's explicitly shared directives.

Verification uses isolated data, scoped tests and a headless browser. `T3CODE_DESKTOP_START_HIDDEN=true` keeps the desktop's initial main window hidden and suppresses the connecting splash. User activation remains available through the usual app controls. No focus or input injection is required for verification.
