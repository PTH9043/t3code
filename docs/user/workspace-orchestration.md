# AI 작업 오케스트레이션

프로젝트 운영 화면의 **멀티 에이전트 협업**은 지휘 AI가 목표를 작업 그래프로 나누고, 독립된 작업을 동시에 실행하며, 선행 결과가 필요한 작업은 검증된 결과가 준비된 뒤 실행합니다. 지휘 AI와 작업 AI의 기록은 하나의 대화에 블록으로 쌓입니다.

오케스트라는 현재 프로젝트와 대화에서 요청한 작업을 관리합니다. “이어서”라고 요청하면 해당 대화에서 진행하던 작업을 이어가며, 과거 기억에 적힌 다른 작업을 새 목표로 삼지 않습니다. 다른 폴더의 공유 기억과 공용 라이브러리는 자동 입력에 넣지 않습니다. 최근 대화에서 목표를 확인할 수 없으면 지휘 AI가 확인 질문을 합니다.

## 질문 먼저

입력창의 **질문 먼저**를 켜면 선택한 **지휘 AI**가 먼저 요청을 받습니다. 프로그램 설명이나 상태를 묻는 질문에는 답변하고 끝납니다. 작업 요청이면 지휘 AI가 확인할 범위와 질문을 제시하며, 사용자 답변 전에는 토론·작업 배정·하위 AI 실행으로 넘어가지 않습니다. **바로 실행**과 **토론 먼저** 양쪽에 적용됩니다.

같은 대화의 질문 카드나 입력창으로 답하면 지휘 AI가 답변을 확인합니다. 실행할 범위가 정해지면 설정한 토론 또는 작업 계획으로 이어지고, “설명만 해”, “작업하지 마”라고 답하면 작업을 시작하지 않습니다. 질문 중에도 오케스트라 중지 버튼을 사용할 수 있습니다. 질문·답변·작업은 기존 대화에 남으며, 이전 질의응답도 다음 요청의 맥락에 포함됩니다.

질문 대기 상태는 서버에 저장됩니다. 다시 접속해도 답변하지 않은 질문이 유지되며, 참가자나 지휘자가 임의로 바뀌지 않습니다. **질문 먼저**를 끄면 기존 토론·바로 실행 설정을 따릅니다.

## 실행 전 계획 확인

채팅의 **AI 작업 → AI가 계획**에서 **실행 전 계획 확인**을 켜면 지휘 AI가 계획을 만든 뒤 작업 시작을 기다립니다. 대화의 작업 목록이나 프로젝트 운영 화면에서 작업 이름·지시·담당 AI·선행 작업을 바꿀 수 있습니다. **계획만 저장**은 실행하지 않고, **이 계획으로 시작**은 저장한 계획으로 진행합니다. 모바일 운영 현황에서도 같은 계획을 수정할 수 있습니다.

기본값은 꺼짐이며 꺼 두면 별도 계획 확인 없이 실행합니다. **질문 먼저**와 **조건 확인**은 각각 기존 설정을 따릅니다. 다른 기기에서 계획을 바꾸거나 이미 시작한 경우 이전 계획의 확인 요청은 적용하지 않습니다. 계획을 직접 수정하는 횟수는 실패 복구 한도를 소모하지 않습니다.

**작업 AI 실행 한도**를 지정하면 실행 단계의 작업·검증·재시도 호출 수를 제한합니다. 질문과 계획 확인 대기는 호출 수에 포함하지 않습니다. 한도에 도달하면 이미 끝난 결과를 보존하고 더 시작하지 않습니다. 토큰 수나 요금 한도와는 별개입니다.

## 장시간 작업과 복구

오케스트라 작업은 일반 대화의 유휴 세션 정리 때문에 종료되지 않습니다. 병렬 작업 하나가 결과를 반환하면 다른 작업이 실행 중이어도 해당 결과와 검증 대기 상태를 저장합니다. 빈 실행 자리가 생기면 선행 조건을 충족한 다음 작업을 바로 시작합니다. 같은 격리 작업 폴더의 수정·검증 작업은 겹쳐 실행하지 않습니다. 서버가 재시작되면 완료된 결과를 재사용하고, 중단된 시도의 진행 표시를 닫은 뒤 보존된 부분 응답을 다음 시도에 전달합니다. 기존 산출물을 먼저 확인하고 남은 지점부터 이어가며, 중단된 시도를 완료된 작업으로 표시하지 않습니다.

AI 실행의 이벤트 연결이 종료되면 중단 사유를 표시하고 복구 절차로 넘어갑니다. 작업 목록에는 현재 시도의 **최근 활동과 수신 시각**이 표시되므로 작업을 접은 상태에서도 마지막으로 받은 진행 기록을 확인할 수 있습니다. 이 시각은 실제 수신 기록이며 새 활동 없이 자동으로 갱신되지 않습니다.

지휘 AI가 답변을 기다리면 목록 상단에 **답변 대기**와 질문이 표시됩니다. 대화 입력창에서 답변하면 이어집니다.

## 에이전트 역할 연결

협업을 시작하기 전에 역할별 계정과 모델을 연결합니다.

대화의 **AI 작업 → AI가 계획**을 열고 **오케스트라 참가자 설정**을 선택한 뒤 계정별 **모델 추가**를 누르면 같은 Codex·Claude 계정의 여러 모델을 함께 선택할 수 있습니다. 참가자는 지휘 AI를 포함해 2~8명이며, 각 모델의 추론 수준을 따로 지정합니다. 모델 옆 제거 버튼으로 참가자를 빼거나 모델을 바꿀 수 있습니다.

상단 **지휘 AI** 목록이나 모델 옆 왕관 버튼으로 지휘자를 고릅니다. 선택한 지휘 AI가 계획·배정·검증·최종 정리를 맡으며 실행 중 임의로 바뀌지 않습니다. 지휘자를 제거하면 첫 참가자가 지휘를 맡습니다.

새 설정은 **바로 실행**, **실패 복구·재계획 1회**, **선택하지 않은 AI 추가 허용 꺼짐**으로 시작합니다. 필요한 경우 토론 방식과 한도를 바꿀 수 있고, 이전에 저장한 설정은 유지됩니다. 추가 허용을 켜면 지휘자가 연결된 다른 모델을 작업에 배정할 수 있으며 실제 담당자는 작업 그래프에 표시됩니다. 화면에서 선택한 추론 수준은 각 모델 실행에 전달됩니다. 이 설정이 모델의 내부 사고량이나 고정된 토큰 절감률을 보장하는 것은 아닙니다.

프로젝트 운영 화면의 역할 연결은 다음 기본 역할을 제공합니다.

- **총괄**: 목표 이해, 작업 그래프 설계와 수정, 검증, 결과 종합, 기억 후보 선택
- **구현 담당**: 코드 작성, 수정, 디버깅, 테스트, 데이터 처리, 자동화 실행
- **조사 담당**: 최신 정보, 뉴스, X, 커뮤니티 동향과 외부 근거 조사

각 역할에 사용할 계정과 모델을 직접 연결합니다. 채팅에서 참가자를 선택한 실행은 그 참가자와 지휘자를 사용합니다. 같은 제공자의 계정을 여러 개 등록해 두면 역할 연결 방식에서는 한 경로가 도구 오류로 실패했을 때 아직 사용하지 않은 같은 종류의 계정으로 다시 시도할 수 있습니다. 필요한 역할이 연결되어 있지 않으면 해당 그래프를 실행하지 않습니다.

## 프로젝트 운영 현황

웹·데스크톱에서 프로젝트 제어센터의 **대화로 돌아가기**를 누르면 그 프로젝트에서 마지막으로 보던 대화로 돌아갑니다. 다른 프로젝트를 방문하거나 화면을 새로고침해도 복귀 대상은 프로젝트별로 유지됩니다. 이전 기록이 없으면 해당 프로젝트의 최근 대화를 열고, 대화가 없으면 같은 프로젝트에서 새 대화를 시작합니다.

각 프로젝트는 대화, 터미널, 프로그램, 장애, 작업 그래프와 자동화를 하나의 운영 화면에 모읍니다. **실행 상태**와 **확인할 상태**는 따로 표시됩니다. 예를 들어 작업이 끝나 실행은 대기 상태여도 아직 보지 않은 완료 결과가 있으면 **새 완료**가 유지됩니다. 사용자가 해당 프로젝트 운영 화면을 열어 확인한 시각은 서버에 저장되므로 다른 기기에서도 같은 완료를 새 알림으로 반복 표시하지 않습니다.

프로그램·장애·협업·스케줄 상세 목록은 고정 간격으로 계속 조회하지 않습니다. 서버가 해당 프로젝트의 운영 변경을 알리면 필요한 목록만 다시 읽습니다. 프로젝트 대화가 계속 출력되는 동안 프로그램 목록까지 불필요하게 갱신되는 일도 없습니다.

웹과 데스크톱의 **프로젝트 터미널**에는 프로젝트에 속한 모든 터미널의 실행 상태, 작업 폴더, 실행 중인 하위 명령, 조작자와 관찰자 수가 표시됩니다. 모바일 프로젝트 운영 화면에서도 같은 터미널을 확인하고 정확한 터미널로 다시 들어갈 수 있습니다. 모바일 앱이 앞에 열려 있을 때는 현재 보고 있는 대화 또는 같은 프로젝트의 활동 알림을 다시 띄우지 않습니다.

## 실행 흐름

새 협업 실행은 다음 순서로 진행됩니다.

1. 선택한 지휘 AI가 현재 요청과 해당 대화의 최근 작업 기록을 먼저 확인하고, 그 작업과 관련된 프로젝트 기억을 참고합니다. 역할 연결 방식에서는 조정자에 연결된 AI가 지휘합니다.
2. 각 작업에 목표, 입력, 제약, 예상 결과, 의존성, 성공 기준을 지정합니다.
3. 서버가 중복 작업, 존재하지 않는 의존성, 순환 의존성과 잘못된 에이전트 배정을 거부합니다.
4. 준비된 독립 작업을 동시에 실행합니다.
5. 선택한 지휘 AI가 작업 AI의 결과를 별도 검증 단계에서 확인합니다.
6. AI가 검토한 결과를 종합하고, 코드 작업은 통합 상태와 실제 검증 명령을 확인한 뒤 완료합니다.

작업 중 새 정보, 정보 부족, 구현 실패, 잘못된 가정, 결과 충돌 또는 검증 실패가 발견되면 지휘 AI가 영향을 받은 경로를 중단하고 복구 작업을 추가합니다. 같은 실패 접근을 무한히 반복하지 않으며, 허용한 참가자와 복구 한도 안에서 다시 시도합니다.

## 한 대화에서 작업 목록 관리

웹·데스크톱 대화에서는 오케스트라 실행마다 **작업 목록** 하나가 표시됩니다. 작업마다 새 대화방을 만들지 않으며, 같은 실행의 재시도도 해당 작업 안에 모입니다. 목록에는 지휘 AI, 작업별 담당 모델과 상태, 아직 시작하지 않은 작업이 함께 표시됩니다.

- **전체 / 실행 중 / 확인 필요 / 완료**로 작업을 걸러 볼 수 있습니다. 실행 중에는 검증을 기다리는 작업도 포함되며, 확인 필요에는 실패와 사용자 답변 대기가 표시됩니다. 필터를 바꿔도 작업 순서를 상태별로 재정렬하지 않습니다.
- 작업 행을 누르면 그 자리에서 지시, 현재 출력, 변경 파일, 도구 실행 기록과 검증 근거를 확인합니다. **이전 시도 보기**에서는 실패한 시도의 출력과 당시 모델도 볼 수 있습니다.
- 완료 작업은 기본적으로 접히고 실행 중·실패·답변 대기 작업은 펼쳐집니다. 직접 접거나 펼친 선택은 상태 변화나 목록 스크롤로 초기화되지 않습니다. **모두 접기 / 모두 펼치기**도 사용할 수 있습니다.
- 필터와 접기 버튼을 조작하면 자동으로 최신 출력까지 따라가는 동작을 멈춰 읽던 내용을 확인할 수 있습니다. 출력이 추가된다는 이유로 작업 행을 위아래로 재정렬하지 않습니다.
- 오래된 메시지가 아직 불러와지지 않았다면 저장된 결과 요약임을 표시합니다. **이전 작업 불러오기**로 원본 메시지가 로드되면 전체 출력이 표시됩니다.

## 신뢰도와 실패 표시

검증 결과에는 **높음**, **중간**, **낮음** 신뢰도가 표시됩니다. 낮은 신뢰도의 결과는 최종 확정에 사용할 수 없으며 추가 조사나 교차 검증 경로가 열립니다.

실패는 정보 부족, 구현 오류, 도구 오류, 잘못된 가정, 검증 실패로 분류됩니다. 제어센터의 그래프에는 현재 단계, 병렬 작업, 계정과 모델, 시도 기록, 검증 근거, 실패 분류, 그래프 수정 이력과 다음 행동이 표시됩니다.

웹과 데스크톱에서는 프로젝트 운영 화면에서 실행을 만들고 관리할 수 있습니다. 모바일에서는 프로젝트의 **운영 현황**에서 같은 그래프를 확인하고, 각 시도의 대화를 열거나 대기·실행 중인 작업을 취소할 수 있습니다.

## 오케스트라 실행과 질문 답변

웹·데스크톱의 **AI 작업**에서 **AI가 계획**과 **저장된 워크플로**를 고르고, 같은 화면에서 참가자와 실행 방식을 설정할 수 있습니다. 채팅 입력으로 계획을 시작하거나 저장된 워크플로를 실행하세요. 모델 선택 메뉴의 **오케스트라**도 이 화면으로 연결됩니다. **단일 AI**로 전환하면 오케스트라 모드가 꺼집니다. 같은 메뉴에서 **지속 작업실**을 선택해 담당 AI와 후속 개발을 이어가는 방식으로 바꿀 수도 있습니다.

오케스트라가 완료되거나 중지·실패하면 기존 대화 맨 아래에 **오케스트라 대화 정리**가 자동으로 표시됩니다. 논의와 결정, 사용자의 추가 요청과 질문 답변, 작업 결과, 저장된 검증 기록과 최종 결과를 함께 정리합니다. 중지·실패한 실행은 남은 내용과 오류도 표시하며, 미완료 작업을 완료로 표시하지 않습니다. 질문 답변을 기다리는 동안에는 종료 요약을 만들지 않습니다. 요약은 서버에 일반 대화 메시지로 저장되어 웹·데스크톱·모바일에서 다시 확인할 수 있습니다.

웹·데스크톱의 회의 설정에서 **오케스트라**를 켜면 지휘 AI의 계획, 각 AI의 작업, 검증과 최종 결과가 **하나의 대화방**에 순서대로 쌓입니다. 작업용 대화방을 추가로 만들지 않습니다. 각 블록에는 담당 AI·모델·상태·작업 지시가 표시되고, 출력은 해당 블록 안에서 갱신됩니다. 웹·데스크톱에서는 블록을 접거나 펼칠 수 있습니다. 재시도는 이전 기록을 보존하면서 새 블록으로 추가됩니다. 모바일에서도 같은 대화와 작업 블록을 확인할 수 있습니다.

병렬 폭은 1~6입니다. **worktree 격리**를 끄면 파일 수정 작업은 한 번에 하나씩 실행합니다. 승인이나 질문에 대한 답변은 요청한 AI에게만 전달되며, 중단 버튼은 해당 오케스트라의 실행을 취소합니다. 종료 처리가 진행되는 동안 작업 목록에는 **중지 중**이 표시되고, 종료 확인 후 **중지됨**으로 바뀝니다. 아직 시작하지 않은 작업도 취소되며, 취소된 AI의 미완료 승인·질문도 함께 닫힙니다. 이미 완료한 작업과 출력 기록은 유지됩니다.

여러 작업이 동시에 질문하면 하나씩 답변을 받습니다. 게시된 질문에 답할 때까지 새 실행 묶음은 시작하지 않으며, 뒤에 기다리는 질문은 제어센터에서 확인할 수 있습니다. 답변은 화면에 표시된 질문의 작업에만 적용됩니다. 다른 기기에 남은 이전 질문의 답변으로 다음 질문을 처리하지 않습니다. 업데이트 후 오래 열어 둔 클라이언트에서 답변 전송이 실패하면 화면을 새로고침하세요.

## worktree 격리와 병합

오케스트라 설정에서 **worktree 격리**를 켜면 파일을 수정하는 작업 묶음(수정 작업, 그 검증 게이트, 뒤이어 같은 결과 위에서 수정하는 작업)마다 전용 git worktree와 브랜치(`t3code/orch-…`)를 만들어 병렬 수정을 허용합니다. 같은 묶음의 작업은 하나의 worktree를 순서대로 사용하므로 후속 작업이 앞선 수정 결과를 그대로 보고, 검증도 실제 수정된 체크아웃에서 실행됩니다. 프로젝트에 worktree 생성 스크립트가 설정되어 있으면 스크립트가 성공(종료 코드 0)해야 그 묶음의 첫 작업이 시작됩니다.

스케줄·장애 복구처럼 사람이 보내지 않는 실행에는 제어센터의 **무인 실행 오케스트라 기본값**(경계·RAG 설정 카드)이 적용됩니다. 기본값을 켜 두면 무인 실행도 지정한 병렬 폭과 worktree 격리로 진행되며, 회의에서 직접 보낸 실행은 항상 전송 시 설정이 우선합니다.

새 실행에서는 격리 작업 폴더의 미반영 변경을 **변경 통합 대기**로 표시하며 전체 실행을 완료로 처리하지 않습니다. 결과 병합은 자동으로 하지 않습니다. 제어센터의 작업 노드 카드에서 **diff 보기**로 worktree와 기준 브랜치의 차이(커밋된 변경과 커밋 전 변경)를 검토하세요. 격리된 작업의 커밋·병합은 카드에 표시된 worktree 경로에서 진행해야 합니다. 공용 대화의 기본 작업 폴더는 프로젝트 폴더입니다. 실행이 끝나면 변경이 남지 않은 worktree는 자동 정리되고, 병합되지 않은 변경이 남은 worktree는 **정리 대기**로 보존됩니다. 검토를 마쳤다면 노드 카드의 **정리** 버튼으로 제거할 수 있습니다(변경이 남아 있으면 보존됩니다). 서버 재시작 시에는 살아 있는 실행이 참조하지 않는 오케스트라 worktree를 점검해 깨끗한 것만 회수합니다.

## 실제 검증과 완료

오케스트라 설정의 **완료 검증 명령**에 프로젝트 폴더에서 실행할 명령을 한 줄에 하나씩 입력합니다. 저장된 실행 프로필의 검증 명령도 실제 실행에 사용됩니다. 코드 작업은 통합된 프로젝트 폴더에서 명령이 성공해야 완료됩니다. 명령이 없거나 실패하면 결과를 보존하고 **검증 명령 필요** 또는 **검증 실패**로 표시합니다. 작업 목록에서 명령을 수정해 **통합 상태 확인 · 다시 검증**을 누르면 끝난 AI 작업을 반복하지 않고 검증만 다시 실행합니다.

검증 기록에는 실제 명령·종료 코드·시간 초과 여부·로그 위치·확인 시각이 남습니다. 검증 도중 코드가 바뀌면 다시 확인해야 합니다. 조사·분석 작업은 작업 폴더가 시작 시점과 같고 미통합 변경이 없으면 코드 검증 명령 없이 끝납니다. 검증 기록과 AI의 검토 기록은 구분해서 표시합니다. 이 완료 확인은 새로 시작한 실행에 적용되며 예전 완료 기록은 유지됩니다.

## 공용·프로젝트·폴더 기억

지식을 저장할 때 **기억 적용 범위**를 선택합니다.

- **공용**: 이 환경에 연결된 모든 프로젝트에서 사용합니다. 다른 서버 환경에는 자동으로 공유되지 않습니다.
- **이 프로젝트**: 이 프로젝트 안에서 사용합니다. 기존에 저장한 기억은 이 범위를 유지합니다.
- **특정 폴더**: 지정한 프로젝트 내부 폴더와 그 하위 경로의 작업에만 사용합니다. 비슷한 이름의 다른 폴더에는 적용되지 않습니다.

검색과 프롬프트 미리보기의 **작업 경로**에 폴더를 입력하면 해당 폴더 기억까지 포함합니다. 경로를 비우면 공용·프로젝트 기억만 사용합니다. 기억 파일을 정리하는 **장기기억의 하위 폴더**는 적용 범위와 별개입니다. 항목을 편집·보관·복원할 수 있으며, 보관한 항목은 프롬프트에 들어가지 않습니다.

AI 도구가 보고한 웹 검색 기록은 출처 링크와 수집 시각을 포함해 프로젝트 장기기억에 저장합니다. 원시 검색 기록은 **미검증**으로 표시하고, 인증 정보 형태의 값은 마스킹합니다. 검증한 결론과 검색 원문을 구별해 사용하세요. 도구가 서버에 전달하지 않은 검색 과정은 수집할 수 없습니다.

## 선택적 기억

전체 작업 기록은 실행 내역에 남지만, 다음 작업의 문맥으로 사용하는 장기 기억은 총괄 모델이 반복 가치가 있다고 선택한 항목만 승격됩니다. 프로젝트 구조, 검증된 설계 결정, 성공·실패 패턴, 신뢰할 수 있는 데이터 출처와 반복되는 작업 흐름이 주요 대상입니다. 일회성 출력과 검증되지 않은 추측은 자동으로 장기 기억이 되지 않습니다.

## 대화 입력 자동 압축 RAG

프로젝트의 제어센터에서 **대화 입력 자동 압축 RAG**를 켜면 웹, 데스크톱, 모바일에서 사용자가 직접 보낸 새 메시지가 해당 프로젝트의 검색 자료로 저장됩니다. 원본 대화는 그대로 유지되고, RAG에는 공백과 반복 블록을 줄인 별도 사본만 들어갑니다. 긴 입력은 설정한 문자 예산에 맞게 제한되며 원문은 대화에서 계속 확인할 수 있습니다.

토큰, 개인 키, API 키와 암호 형태의 값은 기본적으로 마스킹한 뒤 저장합니다. 자동 협업 실행과 프로그램 감시가 내부적으로 만든 프롬프트는 사용자 입력 RAG에 포함하지 않습니다. 같은 대화에서 동일한 내용을 반복해 보내면 같은 RAG 항목으로 합쳐집니다.

자동 수집을 끄면 자동 생성된 RAG 사본과 검색 청크만 제거됩니다. 사용자가 직접 등록한 지식·RAG 자료와 원본 대화는 삭제되지 않습니다. 자동 항목 수와 저장 내용은 웹·데스크톱 제어센터의 **RAG · 메모리 · 장기기억 · 프롬프트**에서 확인하고 개별 보관할 수 있습니다. 모바일에서 보낸 입력도 서버에서 동일하게 처리되지만 세부 관리 화면은 웹·데스크톱 제어센터에서 제공합니다.

## 에이전트 결과 자동 압축 등록

**에이전트 결과 자동 압축 등록**을 켜면 협업 실행이 끝날 때 각 작업 노드가 낸 결과가 빠짐없이 압축되어 이 프로젝트의 검색 자료로 등록됩니다. 총괄 모델이 고른 기억 후보가 "남길 가치가 있다고 판단한 결론"이라면, 이쪽은 조사·구현·검증에서 실제로 나온 산출물 자체의 기록입니다. 기본값은 켜짐입니다.

각 항목에는 해당 작업의 과제, 목표, 성공 기준이 결과 앞에 함께 저장되므로 나중에 검색으로 꺼내 읽어도 맥락이 남습니다. 항목은 `collaboration-outputs` 상대 폴더에 들어가고, 작업 노드마다 항목 하나가 고정된 식별자로 유지되므로 같은 실행을 이어서 진행해도 사본이 늘어나지 않고 갱신됩니다.

압축 방식은 대화 입력 자동 압축과 같습니다. 공백을 정리하고 반복 블록을 제거한 뒤 설정한 문자 예산에 맞게 제한하며, 토큰·개인 키·API 키·암호 형태의 값은 기본적으로 마스킹합니다. 저장된 항목의 태그에는 담당 에이전트, 작업 종류, 신뢰도, 원본 및 저장 문자 수가 남아 어떤 경로에서 나온 자료인지 구분할 수 있습니다.

이 기능을 끄면 이후 실행부터 등록하지 않으며, 이미 등록된 자료는 그대로 남습니다. 필요하면 지식 목록에서 개별 항목을 보관하세요.

## 한국어 검색 품질

프로젝트 RAG는 한국어를 두 글자 조각 단위로 색인하므로 조사나 어미가 붙은 단어도 찾습니다. 예를 들어 "수익"으로 검색하면 "수익률을", "수익이"가 들어간 자료가 모두 나옵니다. 검색어에서도 "대시보드를", "추가해줘" 같은 조사·어미를 떼고 핵심어로 찾으며, "작업", "확인" 같은 요청 말투는 검색어에서 제외합니다. 제목과 태그에 맞는 자료, 질문의 핵심어를 더 많이 담은 자료가 앞에 오고, 같은 자료는 가장 잘 맞는 부분 하나만 표시됩니다.

의미 검색에 필요한 자료 준비는 백그라운드에서 진행합니다. 준비 중에는 키워드 검색과 이미 준비된 자료를 사용하며, 앱을 다시 시작해도 미완료 작업을 이어갑니다. 로컬 임베딩 모델에 연결할 수 없으면 재시도 대기 상태를 안내합니다. 검색 준비나 캐시 정리는 원본 대화와 직접 저장한 기억을 삭제하지 않습니다.

대화 기억 검색은 반복된 근거를 묶어 서로 다른 내용을 더 많이 보여주며, 추가 출처도 조회할 수 있습니다. 최근 사용자 정정과 현재 작업을 우선하고, 영구 규칙은 오래됐다는 이유로 제외하지 않습니다. 과거 시점이나 변경 이력을 물으면 날짜가 다른 반복 기록도 함께 살펴봅니다.

에이전트에게는 짧은 발췌가 아니라 검색된 부분의 본문 전체(최대 약 1,200자)가 전달됩니다. 제어센터 검색 결과에는 일치한 단어가 `[ ]`로 표시된 발췌가 나옵니다.

## 공용 디자인 라이브러리

지식은 지정한 적용 범위를 따릅니다. **공용 디자인 라이브러리**도 모든 프로젝트가 함께 읽습니다. [더씨커 레퍼런스](https://ref.theseeker.io)의 디자인 레퍼런스(AI가 붙인 제목, 요약, 상세 설명, 카테고리, 스타일, 한글 태그, 색상 팔레트, 작가, 원본 게시물 링크)를 텍스트로 저장하며, 이미지는 저장하지 않습니다.

- **수집**: 앱 서버가 처음 실행될 때 전체 레퍼런스를 천천히(동시 요청 3개 이하) 가져오고, 이후 하루에 한 번 새로 추가된 레퍼런스만 가져옵니다. 수집 도중 앱을 껐다 켜면 멈춘 지점부터 이어서 진행합니다.
- **활용**: 협업 실행의 프롬프트를 만들 때 작업 내용과 핵심어가 두 개 이상 겹치거나 제목·태그가 일치하는 레퍼런스만 최대 4개까지, 레퍼런스 링크와 작가 표기를 붙여 넣습니다. 디자인과 관계없는 작업에는 들어가지 않으며, 프로젝트 자체 문맥이 항상 먼저 들어가고 라이브러리는 전체 문맥 예산의 4분의 1을 넘지 않습니다.
- **확인**: 제어센터 **RAG · 메모리 · 장기기억 · 프롬프트**의 **공용 디자인 라이브러리** 카드에서 항목 수, 마지막 동기화 시각, 오류를 확인하고 **지금 동기화**로 즉시 가져올 수 있습니다. **AI 프롬프트 수집·결합 미리보기**에서 화면 관련 작업을 입력하면 **디자인 레퍼런스 N** 배지와 함께 실제로 들어갈 레퍼런스를 볼 수 있습니다.

## 프롬프트 투입 기록

자동 수집은 지식을 빠르게 늘리기 때문에, 쌓인 자료가 실제로 쓰이는지 확인할 수단이 필요합니다. 협업 실행이 프롬프트를 결합할 때마다 그 프롬프트에 실제로 들어간 항목의 투입 횟수와 마지막 투입 시각이 기록됩니다. 제어센터의 지식 목록에는 항목마다 **프롬프트 n회** 또는 **미사용** 표시가 붙습니다.

세는 대상은 모델에 도달한 자료뿐입니다. 제어센터의 프롬프트 결합 미리보기는 같은 방식으로 프롬프트를 만들어 보여주지만 투입으로 기록하지 않습니다. 한 번의 결합에서 같은 항목이 지식 목록과 검색 결과 양쪽으로 들어와도 한 번만 셉니다. 에이전트 결과 자동 등록이 같은 항목을 다시 등록해도 투입 기록은 초기화되지 않습니다.

기능을 켜기 전에 실행된 과거 프롬프트는 어떤 자료를 썼는지 남긴 기록이 없어 투입 횟수가 0에서 시작합니다. 며칠 실행이 쌓인 뒤의 **미사용** 비율이 자동 수집 범위를 좁힐지 판단하는 근거가 됩니다.

압축된 항목은 원본 문자 수와 저장 문자 수, 절감률을 함께 표시합니다.

## 안전 확인

파일 영구 삭제, 실제 금전 이동이나 거래, 중요한 보안 변경, 외부 게시·전송처럼 되돌리기 어렵거나 외부에 영향을 주는 작업은 적용 가능한 사용자 확인 절차가 필요합니다. 예약 실행에는 승인 대기 모드의 역할을 사용할 수 없습니다.

프로그램 오류 수정은 사용자가 **수정·검증 시작**을 지시한 뒤 실행됩니다. 자동 재시작은 구조화된 수정 승인, 낮지 않은 전체 신뢰도, 완료된 수정에 대한 통과 검증이 모두 있을 때만 허용됩니다. 자세한 내용은 [프로젝트 프로그램 운영](./workspace-programs.md)을 참고하세요.

프로젝트별로 상시 감시를 켜 두고 싶다면 [프로그램 모니터링 모드](./program-monitoring.md)를 참고하세요. 이상이 감지되면 전용 모니터링 스레드에 보고하고, 행동은 사람이 승인한 범위 안에서만 합니다.
