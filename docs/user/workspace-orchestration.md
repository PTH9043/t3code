# 페이블 작업 오케스트레이션

프로젝트 운영 화면의 **멀티 에이전트 협업**은 하나의 요청을 고정된 순서로 전달하지 않습니다. 페이블이 목표를 작업 그래프로 나누고, 실제 의존성이 없는 작업은 동시에 실행하며, 선행 결과가 필요한 작업은 검증된 결과가 준비된 뒤 실행합니다.

## 에이전트 역할 연결

협업을 시작하기 전에 역할별 계정과 모델을 연결합니다.

- **페이블**: 목표 이해, 작업 그래프 설계와 수정, 검증, 결과 종합, 기억 후보 선택
- **코덱스**: 코드 작성, 수정, 디버깅, 테스트, 데이터 처리, 자동화 실행
- **그록**: 최신 정보, 뉴스, X, 커뮤니티 동향과 외부 근거 조사

페이블은 **조정자**, 코덱스는 **구현 담당**, 그록은 **조사 담당** 역할에 연결합니다. 같은 제공자의 계정을 여러 개 등록해 두면 한 경로가 도구 오류로 실패했을 때 아직 사용하지 않은 같은 종류의 계정으로 다시 시도할 수 있습니다. 필요한 역할이 연결되어 있지 않거나 잘못된 제공자 종류에 연결되어 있으면 해당 그래프를 실행하지 않습니다.

## 프로젝트 운영 현황

각 프로젝트는 대화, 터미널, 프로그램, 장애, 작업 그래프와 자동화를 하나의 운영 화면에 모읍니다. **실행 상태**와 **확인할 상태**는 따로 표시됩니다. 예를 들어 작업이 끝나 실행은 대기 상태여도 아직 보지 않은 완료 결과가 있으면 **새 완료**가 유지됩니다. 사용자가 해당 프로젝트 운영 화면을 열어 확인한 시각은 서버에 저장되므로 다른 기기에서도 같은 완료를 새 알림으로 반복 표시하지 않습니다.

프로그램·장애·협업·스케줄 상세 목록은 고정 간격으로 계속 조회하지 않습니다. 서버가 해당 프로젝트의 운영 변경을 알리면 필요한 목록만 다시 읽습니다. 프로젝트 대화가 계속 출력되는 동안 프로그램 목록까지 불필요하게 갱신되는 일도 없습니다.

웹과 데스크톱의 **프로젝트 터미널**에는 프로젝트에 속한 모든 터미널의 실행 상태, 작업 폴더, 실행 중인 하위 명령, 조작자와 관찰자 수가 표시됩니다. 모바일 프로젝트 운영 화면에서도 같은 터미널을 확인하고 정확한 터미널로 다시 들어갈 수 있습니다. 모바일 앱이 앞에 열려 있을 때는 현재 보고 있는 대화 또는 같은 프로젝트의 활동 알림을 다시 띄우지 않습니다.

## 실행 흐름

새 협업 실행은 다음 순서로 진행됩니다.

1. 페이블이 사용자 목표와 관련 프로젝트 기억을 확인합니다.
2. 각 작업에 목표, 입력, 제약, 예상 결과, 의존성, 성공 기준을 지정합니다.
3. 서버가 중복 작업, 존재하지 않는 의존성, 순환 의존성과 잘못된 에이전트 배정을 거부합니다.
4. 준비된 독립 작업을 동시에 실행합니다.
5. 페이블이 코덱스와 그록의 결과를 생성자와 분리된 검증 단계에서 확인합니다.
6. 검증된 결과만 최종 응답으로 종합합니다.

작업 중 새 정보, 정보 부족, 구현 실패, 잘못된 가정, 결과 충돌 또는 검증 실패가 발견되면 페이블이 영향을 받은 경로를 중단하고 복구 작업을 추가합니다. 같은 실패 접근을 무한히 반복하지 않으며, 계정 또는 해결 방법을 바꾸어 제한된 횟수만 다시 시도합니다.

## 신뢰도와 실패 표시

검증 결과에는 **높음**, **중간**, **낮음** 신뢰도가 표시됩니다. 낮은 신뢰도의 결과는 최종 확정에 사용할 수 없으며 추가 조사나 교차 검증 경로가 열립니다.

실패는 정보 부족, 구현 오류, 도구 오류, 잘못된 가정, 검증 실패로 분류됩니다. 제어센터의 그래프에는 현재 단계, 병렬 작업, 계정과 모델, 시도 기록, 검증 근거, 실패 분류, 그래프 수정 이력과 다음 행동이 표시됩니다.

웹과 데스크톱에서는 프로젝트 운영 화면에서 실행을 만들고 관리할 수 있습니다. 모바일에서는 프로젝트의 **운영 현황**에서 같은 그래프를 확인하고, 각 시도의 대화를 열거나 대기·실행 중인 작업을 취소할 수 있습니다.

## 오케스트라 실행과 질문 답변

웹·데스크톱의 회의 설정에서 **오케스트라**를 켜면 실행 작업마다 별도 대화를 사용합니다. 병렬 폭은 1~6이며, 재시도와 질문 후 재개는 해당 작업의 대화에서 이어집니다. **worktree 격리**를 끄면 파일 수정 작업은 한 번에 하나씩 실행합니다.

여러 작업이 동시에 질문하면 하나씩 답변을 받습니다. 게시된 질문에 답할 때까지 새 실행 묶음은 시작하지 않으며, 뒤에 기다리는 질문은 제어센터에서 확인할 수 있습니다. 답변은 화면에 표시된 질문의 작업에만 적용됩니다. 다른 기기에 남은 이전 질문의 답변으로 다음 질문을 처리하지 않습니다. 업데이트 후 오래 열어 둔 클라이언트에서 답변 전송이 실패하면 화면을 새로고침하세요.

## worktree 격리와 병합

오케스트라 설정에서 **worktree 격리**를 켜면 파일을 수정하는 작업 묶음(수정 작업, 그 검증 게이트, 뒤이어 같은 결과 위에서 수정하는 작업)마다 전용 git worktree와 브랜치(`t3code/orch-…`)를 만들어 병렬 수정을 허용합니다. 같은 묶음의 작업은 하나의 worktree를 순서대로 사용하므로 후속 작업이 앞선 수정 결과를 그대로 보고, 검증도 실제 수정된 체크아웃에서 실행됩니다. 프로젝트에 worktree 생성 스크립트가 설정되어 있으면 스크립트가 성공(종료 코드 0)해야 그 묶음의 첫 작업이 시작됩니다.

결과 병합은 자동으로 하지 않습니다. 제어센터의 작업 노드 카드에서 **diff 보기**로 worktree와 기준 브랜치의 차이(커밋된 변경과 커밋 전 변경)를 검토한 뒤, 해당 대화의 소스 제어 흐름으로 커밋·푸시하세요. 실행이 끝나면 변경이 남지 않은 worktree는 자동 정리되고, 병합되지 않은 변경이 남은 worktree는 **정리 대기**로 보존됩니다. 검토를 마쳤다면 노드 카드의 **정리** 버튼으로 제거할 수 있습니다(변경이 남아 있으면 보존됩니다). 서버 재시작 시에는 살아 있는 실행이 참조하지 않는 오케스트라 worktree를 점검해 깨끗한 것만 회수합니다.

## 선택적 기억

전체 작업 기록은 실행 내역에 남지만, 다음 작업의 문맥으로 사용하는 장기 기억은 페이블이 반복 가치가 있다고 선택한 항목만 승격됩니다. 프로젝트 구조, 검증된 설계 결정, 성공·실패 패턴, 신뢰할 수 있는 데이터 출처와 반복되는 작업 흐름이 주요 대상입니다. 일회성 출력과 검증되지 않은 추측은 자동으로 장기 기억이 되지 않습니다.

## 대화 입력 자동 압축 RAG

프로젝트의 제어센터에서 **대화 입력 자동 압축 RAG**를 켜면 웹, 데스크톱, 모바일에서 사용자가 직접 보낸 새 메시지가 해당 프로젝트의 검색 자료로 저장됩니다. 원본 대화는 그대로 유지되고, RAG에는 공백과 반복 블록을 줄인 별도 사본만 들어갑니다. 긴 입력은 설정한 문자 예산에 맞게 제한되며 원문은 대화에서 계속 확인할 수 있습니다.

토큰, 개인 키, API 키와 암호 형태의 값은 기본적으로 마스킹한 뒤 저장합니다. 자동 협업 실행과 프로그램 감시가 내부적으로 만든 프롬프트는 사용자 입력 RAG에 포함하지 않습니다. 같은 대화에서 동일한 내용을 반복해 보내면 같은 RAG 항목으로 합쳐집니다.

자동 수집을 끄면 자동 생성된 RAG 사본과 검색 청크만 제거됩니다. 사용자가 직접 등록한 지식·RAG 자료와 원본 대화는 삭제되지 않습니다. 자동 항목 수와 저장 내용은 웹·데스크톱 제어센터의 **RAG · 메모리 · 장기기억 · 프롬프트**에서 확인하고 개별 보관할 수 있습니다. 모바일에서 보낸 입력도 서버에서 동일하게 처리되지만 세부 관리 화면은 웹·데스크톱 제어센터에서 제공합니다.

## 에이전트 결과 자동 압축 등록

**에이전트 결과 자동 압축 등록**을 켜면 협업 실행이 끝날 때 각 작업 노드가 낸 결과가 빠짐없이 압축되어 이 프로젝트의 검색 자료로 등록됩니다. 페이블이 고른 기억 후보가 "남길 가치가 있다고 판단한 결론"이라면, 이쪽은 조사·구현·검증에서 실제로 나온 산출물 자체의 기록입니다. 기본값은 켜짐입니다.

각 항목에는 해당 작업의 과제, 목표, 성공 기준이 결과 앞에 함께 저장되므로 나중에 검색으로 꺼내 읽어도 맥락이 남습니다. 항목은 `collaboration-outputs` 상대 폴더에 들어가고, 작업 노드마다 항목 하나가 고정된 식별자로 유지되므로 같은 실행을 이어서 진행해도 사본이 늘어나지 않고 갱신됩니다.

압축 방식은 대화 입력 자동 압축과 같습니다. 공백을 정리하고 반복 블록을 제거한 뒤 설정한 문자 예산에 맞게 제한하며, 토큰·개인 키·API 키·암호 형태의 값은 기본적으로 마스킹합니다. 저장된 항목의 태그에는 담당 에이전트, 작업 종류, 신뢰도, 원본 및 저장 문자 수가 남아 어떤 경로에서 나온 자료인지 구분할 수 있습니다.

이 기능을 끄면 이후 실행부터 등록하지 않으며, 이미 등록된 자료는 그대로 남습니다. 필요하면 지식 목록에서 개별 항목을 보관하세요.

## 프롬프트 투입 기록

자동 수집은 지식을 빠르게 늘리기 때문에, 쌓인 자료가 실제로 쓰이는지 확인할 수단이 필요합니다. 협업 실행이 프롬프트를 결합할 때마다 그 프롬프트에 실제로 들어간 항목의 투입 횟수와 마지막 투입 시각이 기록됩니다. 제어센터의 지식 목록에는 항목마다 **프롬프트 n회** 또는 **미사용** 표시가 붙습니다.

세는 대상은 모델에 도달한 자료뿐입니다. 제어센터의 프롬프트 결합 미리보기는 같은 방식으로 프롬프트를 만들어 보여주지만 투입으로 기록하지 않습니다. 한 번의 결합에서 같은 항목이 지식 목록과 검색 결과 양쪽으로 들어와도 한 번만 셉니다. 에이전트 결과 자동 등록이 같은 항목을 다시 등록해도 투입 기록은 초기화되지 않습니다.

기능을 켜기 전에 실행된 과거 프롬프트는 어떤 자료를 썼는지 남긴 기록이 없어 투입 횟수가 0에서 시작합니다. 며칠 실행이 쌓인 뒤의 **미사용** 비율이 자동 수집 범위를 좁힐지 판단하는 근거가 됩니다.

압축된 항목은 원본 문자 수와 저장 문자 수, 절감률을 함께 표시합니다.

## 안전 확인

파일 영구 삭제, 실제 금전 이동이나 거래, 중요한 보안 변경, 외부 게시·전송처럼 되돌리기 어렵거나 외부에 영향을 주는 작업은 적용 가능한 사용자 확인 절차가 필요합니다. 예약 실행에는 승인 대기 모드의 역할을 사용할 수 없습니다.

프로그램 오류 수정은 사용자가 **수정·검증 시작**을 지시한 뒤 실행됩니다. 자동 재시작은 구조화된 수정 승인, 낮지 않은 전체 신뢰도, 완료된 수정에 대한 통과 검증이 모두 있을 때만 허용됩니다. 자세한 내용은 [프로젝트 프로그램 운영](./workspace-programs.md)을 참고하세요.

프로젝트별로 상시 감시를 켜 두고 싶다면 [프로그램 모니터링 모드](./program-monitoring.md)를 참고하세요. 이상이 감지되면 전용 모니터링 스레드에 보고하고, 행동은 사람이 승인한 범위 안에서만 합니다.
