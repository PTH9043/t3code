# 프로그램 모니터링 모드

프로젝트마다 켜고 끌 수 있는 상시 감시입니다. 켜 두면 대화를 이어가는 동안에도 서버가 등록된 프로그램의 상태를 계속 지켜보고, 이상이 있으면 프로젝트 전용 **모니터링 스레드**에 보고한 뒤 거기서 무엇을 할지 묻습니다.

## 켜는 방법

제어센터의 **모니터링** 영역에서 스위치를 켭니다. 사이드바의 프로젝트 운영 상태 버튼에도 모니터링 상태가 함께 표시됩니다.

켜면 첫 점검 때 모니터링 스레드가 만들어지고, AI가 프로젝트를 읽기 전용으로 분석해 **감시 계획**을 제안합니다. 계획에는 무엇을(대상), 어떤 기준으로(지표와 창·한도), 이상이 있을 때 무엇을 해도 되는지(플레이북)가 들어 있습니다. 제안은 모니터링 스레드(웹·데스크톱·모바일)와 제어센터 양쪽에 나타나며, **승인**을 눌러야 감시가 시작됩니다.

AI가 계획을 내지 못하고 제안이 실패하면 다음 점검 때 자동으로 다시 시도하지 않습니다. 같은 실패가 점검 주기마다 반복되어 AI 실행을 계속 소모하지 않게 하기 위해서입니다. 감시 AI나 계정 상태를 확인한 뒤 **다시 분석**을 누르거나 모니터링을 껐다 켜면 다시 제안합니다.

모니터링 스레드를 만들려면 프로젝트의 **운영 진단** 또는 **총괄 조정** 역할에 AI 계정이 연결돼 있어야 합니다.

## 감시 계획

- **대상**: 등록된 프로그램, 프로젝트 폴더에서 발견된 프로세스나 URL, 프로그램이 쓰는 **로그 파일**(경로 + 정규식 패턴), 그리고 서버 전역 설정에서 지정한 경우 T3 Code 자체(서버, 데스크톱이 호스트이면 데스크톱 프로세스).
- **지표**: CPU·메모리·응답 지연·느린 내부 처리·실패한 내부 처리·상태검사·코드 변경 후 회귀·**로그 패턴 일치 줄 수**. 각 지표는 임계치, 증가 추세, 직전 창 대비 p95 중 하나의 기준과 분 단위 창을 가집니다. 느리거나 실패한 내부 처리 수는 T3 서버 감시에서만 사용할 수 있으며, 하나의 오류가 여러 내부 처리에 잡힐 수 있습니다.
- **플레이북**: 어떤 지표의 이상에 어떤 조치(알리기만, 프로그램 재시작·중지·시작, 수정·검증 run)를 연결합니다.

계획은 제어센터에서 **직접 편집**할 수도 있습니다. 직접 저장한 계획은 바로 승인된 것으로 봅니다. 프로그램을 추가하거나 삭제하면 승인된 계획은 **재분석 권장** 상태가 되며, 이 상태에서는 기존 계획으로 관찰하되 자동 조치는 실행하지 않습니다. **다시 분석**을 눌러 새 계획을 제안하고 승인받는 동안에도 기존 승인 계획으로 계속 관찰합니다. 이 기간에는 이전 계획의 자동 조치를 실행하지 않으며, 새 계획을 승인하면 새 계획으로 바뀝니다.

## 감시 AI와 감시 스레드

제어센터의 모니터링 카드에서 **감시 AI**(CLI 계정과 모델)를 고릅니다. 비워 두면 프로젝트의 운영자/조정자 역할 바인딩을 씁니다. 감시 계획 제안, 발견 보고, 질문, 그리고 감시 스레드에서 나누는 대화를 모두 이 AI가 맡습니다. 로그 tail·상태 수집은 서버가 직접 하므로 감시 AI에게 Monitor 같은 도구가 없어도 되고, 대화 세션이 끝나거나 서버가 재시작돼도 감시는 이어집니다.

감시 AI의 보고와 질문은 프로젝트마다 하나뿐인 **감시 스레드**(`모니터링 · 프로젝트명`)에 쌓입니다. 사이드바에서는 눈 아이콘과 함께 항상 프로젝트 목록 맨 위에 있고, 거기서 감시 AI와 직접 대화할 수 있습니다. 다른 대화에서 작업하는 중에 감시 스레드에 새 보고나 질문이 생기면, 보고 있는 대화의 입력창 위에 **"감시 AI의 새 보고"** 배너가 떠서 바로 이동할 수 있습니다. 감시 스레드를 열어 보면 배너는 사라집니다.

## 로그 파일 감시

감시 계획의 `log` 대상은 파일 경로와 정규식 패턴(최대 8개)을 가집니다. 서버가 계획 승인 이후에 새로 쓰인 줄만 읽어 패턴에 맞는 줄을 세고, `로그 패턴` 지표가 한도를 넘으면 해당 줄들을 증거로 붙여 감시 AI에게 보고 턴을 엽니다. 파일이 바뀌거나(로테이션) 잠시 없어져도 다음 점검에서 이어 갑니다.

## AI 행동 범위

- **관찰·진단만**: 이상이 감지되면 AI가 원인과 권장 조치를 정리합니다. 프로그램 시작·중지·재시작 제안은 제어센터에서 직접 실행할 수 있습니다. AI의 제안만으로는 프로그램이 제어되지 않습니다.
- **승인한 플레이북 안에서 자율**: 계획을 승인할 때 플레이북도 함께 승인합니다. 이상이 감지되면 서버가 해당 규칙을 먼저 실행하고, AI는 무엇을 왜 했는지 보고하며 규칙 밖의 결정은 묻습니다. **설정 → 권한 → 프로젝트 프로그램 운영**의 **모니터링 자동 조치**가 켜져 있어야 실제로 실행됩니다.

## 점검 주기와 예산

점검 주기(15초~1시간)와 AI 턴 예산(시간당·하루)을 직접 정합니다. 신호 수집과 추세 판단은 서버가 하므로 비용이 들지 않습니다. 예산은 이상이 감지돼 AI가 보고·질문하는 턴에만 쓰이며, 소진되면 발견은 스레드에 보류로 남고 예산이 돌아오면 다시 보고합니다. 같은 이상이 계속되면 30분(지표 창이 더 길면 그 길이)마다만 다시 보고합니다.

AI가 앞선 이상을 진단하는 동안에도 상태와 로그는 계속 확인합니다. 그 사이 발견한 이상은 기존 진단이 끝난 뒤 보고하며, 자동 조치는 다시 확인한 현재 상태에만 적용합니다. 보고되지 않은 발견은 저장되며 서버를 다시 시작해도 복구됩니다. 다만 서버가 꺼져 있던 시간의 상태나 로그는 이 기능이 실시간으로 관찰하지 못합니다. 발견을 보고한 직후 저장 확인 전에 종료되면 같은 발견을 AI가 다시 진단할 수 있습니다. 자동 조치의 발행 도중 중단돼 실제 처리 여부가 불확실하면 같은 발견의 조치를 즉시 다시 보내지 않고 확인이 필요하다고 보고합니다.

**오류 발생 시 읽기 전용 AI 자동 진단** 권한이 꺼져 있으면 모니터링은 AI 턴을 시작하지 않고 스레드에 기록만 남깁니다.

## 코드 변경 후 회귀

계획에 회귀 지표가 있으면 프로젝트의 브랜치나 작업 트리가 바뀔 때마다(1분 단위로 확인) 프로그램에 등록한 **필수 검증 명령**을 순서대로 실행합니다. 실패하면 다음 점검에서 실패한 명령과 출력 꼬리를 모니터링 스레드에 보고합니다. 검증 명령을 등록하지 않은 프로젝트에서는 아무것도 실행하지 않습니다.

## URL과 응답 지연

계획에 URL 대상이 있거나 프로그램의 응답 지연 지표가 있으면 점검마다 해당 주소(프로그램은 등록된 HTTP 상태검사 주소)에 한 번 요청해 응답 시간과 연속 실패 횟수를 잽니다.

## T3 Code 자체 감시

**설정 → 권한 → T3 Code 자체 감시**를 켜면 서버 자체(이벤트 루프 지연, 느린 작업, 메모리·CPU — 데스크톱 앱이 호스트이면 데스크톱 프로세스까지)도 감시 대상이 됩니다. 발견은 거기서 고른 프로젝트(비워 두면 모니터링이 켜진 첫 프로젝트)의 모니터링 스레드 하나로만 갑니다. 켠 뒤 그 프로젝트에서 **다시 분석**을 누르면 계획에 서버 대상이 들어옵니다.

## 끄기

스위치를 끄면 점검이 멈춥니다. 모니터링 스레드와 승인된 계획은 남아 있어 다시 켜면 같은 스레드와 계획으로 이어집니다. 모니터링 스레드를 삭제하면 다음 점검 때 새 스레드를 만듭니다.
