# 새 프로그램을 위한 서버 검증 환경

`experiments/server-probe-bot`은 이번 검증을 위해 새로 만든 독립 프로그램이다. 합성 숫자 작업을 처리하고 결과를 SQLite에 저장한다. 기존 T3 런타임, 다른 프로젝트의 봇, 운영 DB와 계정은 사용하지 않는다.

`infra/server/lab`의 관리 도구는 이 프로그램의 빌드, 후보 검증, 배포 전환, 실패 격리, 롤백과 중지·재시작을 담당한다. Node 24와 Linux Docker Engine을 사용한다. Windows에서는 모든 명령을 CMD에서 실행할 수 있다. 외부 Node 패키지 설치는 필요 없다.

## 실행

저장소 루트에서 실행한다.

```cmd
node infra/server/lab/cli.mjs build --version 0.1.0
node infra/server/lab/cli.mjs deploy --image newautousage-probe-bot:0.1.0-complete
node infra/server/lab/cli.mjs status
```

배포 결과의 `origin`은 이 실험 환경만의 주소다. 프록시 포트는 처음에 loopback의 빈 포트를 선택해 기록하며, 버전 전환과 중지·재시작에서 같은 포트를 재사용한다. 해당 포트를 다른 프로그램이 점유하면 기존 프로그램을 종료하지 않고 시작 오류로 알린다. `/ready`는 실제 작업 진행을, `/status`는 버전·처리량·현재 실행을, `/jobs/<id>`는 저장한 결과를 보여준다. 주소를 브라우저에서 여는 것은 필수가 아니다.

기본 기록 위치는 `.t3/server-lab`이다. `--state-dir`로 다른 실험을 분리할 수 있다. 같은 디렉터리의 변경 작업은 배타적 잠금으로 보호한다. 이미 실행 중인 다른 작업의 잠금은 지우지 않는다. 관리 도구가 비정상 종료된 뒤 소유 프로세스가 존재하지 않는 잠금만 회수한다.

## 후보 검증과 미완성 봇

각 후보는 새 컨테이너와 독립 데이터 볼륨에서 시작한다. 상태 검사가 통과하고, 시험 작업의 실제 결과와 중복 요청 처리가 맞아야 프록시가 새 후보로 전환된다. 이때까지 기존 정상 버전을 유지한다. 준비 실패·반복 종료·잘못된 결과는 실패 기록과 로그를 저장한 뒤 후보를 중지하고 격리한다.

배포마다 고유한 이미지 태그를 추가해 원본 태그가 새 빌드로 바뀌어도 실행한 이미지를 보존한다. 컨테이너 교체는 이 고정 참조를 사용한다. 프록시를 전환하거나 이전 버전으로 복구할 때에는 해당 봇의 현재 상태와 결과를 다시 검사하고, 공개 경로의 실행 ID가 검사한 봇의 실행 ID와 같은지도 확인한다.

```cmd
node infra/server/lab/cli.mjs build --version 0.2.0
node infra/server/lab/cli.mjs deploy --image newautousage-probe-bot:0.2.0-complete
node infra/server/lab/cli.mjs rollback
```

미완성 예제는 이미지 빌드가 성공해도 실제 처리 단계가 구현되지 않아 준비 검사를 통과하지 못한다. 정상 버전을 바꾸지 않는 실패 사례로 보관된다.

```cmd
node infra/server/lab/cli.mjs build --version 0.3.0 --variant incomplete
node infra/server/lab/cli.mjs deploy --image newautousage-probe-bot:0.3.0-incomplete
```

`broken-build` 변형은 의도적으로 잘못된 모듈을 생성한다. 빌드 단계에서 거부되어 실행 이미지로 승격되지 않는다. `--fault crash-loop`는 별도 후보에서 반복 종료를 시험하는 옵션이다.

## 자원과 실패 복구

- 봇마다 RAM 256 MiB, CPU 0.5개, PID 64개를 적용한다. 커널의 실제 제한도 검증한다. 프록시는 RAM 64 MiB와 CPU 0.25개를 사용한다.
- 프로그램은 UID/GID 1000으로 실행한다. 루트 파일시스템은 읽기 전용이고 Linux capability를 제거한다. `/tmp`는 16 MiB이며 프로그램 데이터만 전용 `/data` 볼륨에 쓴다.
- 프록시는 공식 Caddy 실행 파일의 파일 권한과 호환되도록 `NET_BIND_SERVICE`만 허용한다. 봇은 모든 capability를 제거한 상태를 유지한다. [Caddy 공식 이미지의 파일 권한 논의](https://github.com/caddyserver/caddy-docker/issues/396). 프록시의 내부 관리 API 준비 상태도 확인한 뒤 접속 포트를 기록한다.
- 봇은 내부 Docker 네트워크 한 개에만 연결한다. 프록시만 별도의 접속용 네트워크에도 연결해 loopback 포트를 제공한다. 봇의 포트, 호스트 프로젝트 경로와 Docker 소켓을 공개하지 않는다. 외부 서비스와 연결하는 일반 봇을 배포하는 구성은 아니다.
- 별도 부모 프로세스가 자식의 작업 완료 영수증을 감시한다. 진행이 멈추면 소유한 자식만 종료한다. Docker는 실패 시 최대 3번 재시작한다. 건강 상태 표시만으로 자동 재시작되는 것으로 취급하지 않는다.
- 로그는 컨테이너당 파일 1 MiB × 3개로 회전한다. 봇은 최근 작업 1,000개만 저장하고 WAL을 주기적으로 정리한다. 이 보관 정책은 Docker 볼륨의 파일시스템 하드 쿼터를 대신하지 않는다.
- 중지·삭제 대상은 생성할 때 기록한 전체 컨테이너 ID와 생성 시각·소유 식별자를 확인한다. 이름 패턴으로 다른 프로그램을 찾아 종료하지 않는다.

한 후보가 준비되지 않으면 기존 버전의 주소를 유지한다. 버전 전환은 프록시 설정 검증과 재적용 뒤 실제 `/ready` 응답까지 확인한다. 후보와 이전 버전은 각각의 데이터를 보관하며 자동으로 데이터를 합치거나 스키마를 이전하지 않는다. 롤백은 이전 버전과 그 버전의 데이터로 복귀한다.

## 중지·재시작·컨테이너 교체

```cmd
node infra/server/lab/cli.mjs stop
node infra/server/lab/cli.mjs start
node infra/server/lab/cli.mjs replace
node infra/server/lab/cli.mjs status
```

`stop`은 이 환경이 기록한 프로그램만 중지하고 데이터와 실패 증거를 보관한다. `start`는 승인된 버전을 시작하고 프록시를 해당 버전으로 다시 맞춘다. `replace`는 같은 이미지·같은 볼륨으로 컨테이너를 교체한다. 동일 볼륨에 두 프로세스를 동시에 실행하지 않으므로 교체 중에는 짧은 중단이 있다. 서로 다른 데이터 버전 간의 일반 업그레이드는 후보 검증 후 프록시 전환 경로를 사용한다.

복구 후에는 `status`와 실제 `/ready` 응답을 함께 확인한다. 계정·DB·프로젝트 경로가 있는 실제 봇을 이 예제에 자동 연결하지 않는다. 다른 프로그램을 추가할 때에는 전용 이미지, 시뮬레이션 입력, 진행 영수증과 독립적인 결과 검사를 먼저 준비한다.

`scheduled-`로 시작하는 작업 ID는 내부 예약 처리 전용이다. 수동 요청이 이 ID를 선점하면 예약 처리가 멈출 수 있으므로 HTTP 입력에서 거부한다. 수동 작업에는 다른 접두사를 사용한다.

## 반복 가능한 검증

```cmd
node --test experiments/server-probe-bot/job.test.mjs infra/server/lab/manager.test.mjs
node infra/server/lab/verify.mjs --state-dir .t3/server-lab-validation-new
```

통합 검증은 새로운 기록 디렉터리를 요구한다. 완료 후 그 환경의 정상 봇을 유지하므로 `--state-dir`를 지정한 `stop`으로 종료할 수 있다. 이미 있는 기록을 지우고 다시 실행하지 않는다.

검증 항목은 다음과 같다.

1. 정상 버전 2개, 미완성 버전과 잘못된 결과를 내는 버전의 실제 이미지 빌드.
2. 산술 결과, 중복 요청, 같은 ID의 다른 입력, 잘못된 입력.
3. 동시 요청 8개로 총 200개 작업 처리와 지연 측정.
4. 커널의 메모리·PID 제한, 읽기 전용 파일시스템, 사용자·네트워크·소유 경계.
5. 자식 강제 종료와 강제 정지 후 감시기·재시작·저장 결과 복구.
6. 같은 접속 주소에서 버전 전환과 이전 데이터로 롤백.
7. 미완성 후보·잘못된 결과를 내는 후보·반복 종료 후보·빌드 오류가 정상 버전을 교체하지 못하는지 확인.
8. 컨테이너 교체와 명시적인 중지·재시작 후 결과 보존.
9. 120회의 연속 예약 작업 동안 예기치 않은 재시작·OOM 없이 진행하는지 확인.

추가 회귀 검증은 수동 ID 충돌 뒤에도 같은 실행에서 예약 처리가 계속되는지, 자동 복구 직후 실패 후보를 거부해도 정상 봇으로 돌아오는지를 포함한다. 이미지 참조 보존은 다음 명령으로 별도 검증한다. 원본 임시 태그를 다른 버전으로 바꾼 뒤 컨테이너를 교체하고, 이전 이미지·데이터·주소가 유지되는지 검사한다. 이 검증 환경은 완료 후 중지한다.

```cmd
node infra/server/lab/verify-image-pin.mjs --state-dir .t3/new-image-pin-verification
```

검증은 Docker 건강 상태 이벤트와 완료 영수증을 기다린다. 임의로 오래 쉬었다가 성공으로 판정하지 않는다. `verification.json`에는 통과·실패 항목, 실제 이미지·컨테이너 식별자, 지연, 자원 측정과 검증 한계를 남긴다. 실패한 후보의 stdout/stderr와 사유는 `releases/<id>/`에 보관한다. `events.ndjson`은 배포·격리·복구 이력을 기록한다.

기본 실험 환경에 배포한 뒤 보관 상한과 더 긴 연속 처리를 따로 검증할 수 있다.

```cmd
node infra/server/lab/soak.mjs --ticks 360 --retention-jobs 1100
```

이 명령은 실제로 합성 작업 1,100개를 추가한다. 오래된 시험 결과는 1,000개 보관 정책에 따라 정리된다. 모든 새 작업의 결과를 검사하고, 오래된 작업의 제거와 최신 작업의 보존을 확인한 뒤 예약 작업 360회가 완료될 때까지 기다린다. 최대 120회 단위의 완료 영수증마다 실행 ID·재시작 횟수·건강 상태·메모리·데이터 파일 크기를 기록한다. 결과는 실행별 `soak-<id>.json`에 남긴다. `--ticks`는 10~3,600, `--retention-jobs`는 1,100~10,000 범위다.

## 서버로 전달

2026-10-18 최종 통합 실행은 `.t3/server-lab-validation-20261018-06/verification.json`에 기록했다. 17개 항목을 통과했고, 동시 요청 8개의 200개 작업에서 p95는 51ms였다. 별도의 이미지 태그 변경·컨테이너 교체 회귀 검증도 통과했다. 이전 실행의 실패 기록은 수정 경위를 확인할 수 있도록 보존했다. 초기 프록시 실행 권한, 내부 네트워크에서의 포트 공개, 재시작 시 포트 변경, 예약 작업 ID 충돌, 원본 이미지 참조 소실 문제를 이 과정에서 수정했다.

동일한 최종 이미지의 추가 검증에서는 동시 요청 8개로 1,100개 작업을 처리했고 p95는 98ms였다. 저장 작업은 1,000개로 유지됐다. 이어서 360초 동안 예약 작업 360개를 완료했으며 예기치 않은 재시작과 OOM은 없었다. 관측한 cgroup 최대 메모리는 약 69 MiB로 제한 256 MiB 안에 있었다. 이 결과는 `.t3/server-lab/soak-4580d6de-3a6f-4bff-bae3-029ff0a80ad2.json`에 있다.

전달 패키지는 `.t3/server-lab-kit-20261018-final`이다. `START-HERE.txt`에 새 서버의 이미지 불러오기·배포·중지·재시작·롤백 절차가 있고, `manifest.json`에 실제 이미지 식별자와 소스 해시, `archive.json`에 약 81 MB 이미지 묶음의 SHA256이 있다. 이미지 묶음을 다시 불러와 네 이미지의 복원도 확인했다. `verification/`은 검증 증거이며 새 서버의 실행 상태로 복사하지 않는다.

원격 서버 주소가 지정되기 전에는 이 PC의 Docker Linux 환경에서 검증한다. 실제 서버에는 검증한 봇 이미지, 고정한 Caddy 이미지의 참조, `infra/server/lab`, `experiments/server-probe-bot`과 이 문서를 전달한다. 원격 서버의 새 기록 디렉터리에서 `deploy`를 실행한다. PC의 실험용 `state.json`을 복사하면 컨테이너 ID와 볼륨이 달라지므로 새 서버의 실행 기록으로 사용하지 않는다.

이 검증은 합성 작업을 처리하는 새 봇과 이 배포 경로의 결과다. 장기간 운영, 실제 거래소·계정, 외부 네트워크가 필요한 봇, 디스크 장애, 물리 서버 재부팅, ARM64와 실제 도메인의 TLS 품질까지 검증한 결과는 아니다.
