## 코드와 관측의 한계

- `WorkspaceMonitoringReactor.tailLogs`는 최초 파일 조회 실패 때 상태 항목도 만들지 않고 반환한다. 이미 추적하던 파일의 읽기 실패는 `lastError`에 저장하지만, 지표 샘플러는 이 오류를 표시·보고하지 않는다. 따라서 최근 점검 시각만으로 수집 성공을 판단할 수 없다.
- 현재 상태 요약은 실패를 실행 중보다 우선한다. 실제 `__OIBOT`·`__DailyPipeline`의 실행 중 작업과 과거 실패가 동시에 있을 때 프로젝트는 ‘실패’였다. 이는 원본 테스트에서도 요구하는 우선순위이므로 임의로 버그라 단정해 바꾸지 않았다. 현재 활동과 남은 오류를 함께 읽어야 한다.
- 확인한 프로그램 감독·감시 코드에는 실제 데스크톱 창의 렌더링·시각적 오류·탐색기 드래그 성공을 자동 검증하는 경로가 없다. 프로세스·HTTP·로그·추세 신호와 실제 기능 성공은 서로 다른 증거다.
- 추적 진단에는 존재하지 않는 `D:/__NAISWEB` 작업 루트의 자산 접근 오류, Gemini 인증·모델 조회 실패가 있었다. 진단 API에 수집된 오류가 자동 수리됐다는 의미는 아니다.
- 제한적으로 보이는 `server.getProcessDiagnostics`의 0개 결과는 신호를 보낼 수 있는 일부 프로세스 분류만 필터링한 값이다. 전체 수집 결과 93개와 같아야 하는 API가 아니다.

## 이미지 드롭의 현재 상태

사용자는 앞선 재수정 뒤에도 이미지 드롭이 실패한다고 다시 보고했다. **미해결 상태다.** 기존 메시지 주입·headless 검사와 OLE 등록 확인만으로 실제 탐색기 제스처 성공을 주장할 수 없다. 21:18 KST 확인 당시 운영 로그에는 준비 완료만 있었고 정상 파일 수신 기록은 없었다. 렌더러의 `Chrome_RenderWidgetHostHWND`는 파일 수신 스타일이 없었으며, 이는 추가 확인할 대상이지 검증된 단일 원인으로 단정하지 않는다.

PC에는 T3 `D:/__NewAutoUsage/.../electron.exe`와 NAIS3 `D:/__NAIS/NAIS3/win-unpacked/NAIS3.exe`가 각각 실행 중이다. 실제 놓으려는 창이 어느 앱인지 사용자에게 확인을 요청했다. 현재 앞에 있는 창이 NAIS3라는 사실만으로 사용자의 의도한 대상을 단정하지 않았고, NAIS3는 수정하지 않았다.
