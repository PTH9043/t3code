# Windows 이미지 드롭의 렌더러 수신 수정 — 2026-10-23

사용자 증상은 `+` 파일 선택창은 열리지만 탐색기에서 사진을 놓으면 첨부 미리보기가 나타나지 않는 것이다. 앞선 최상위 창만의 `WM_DROPFILES` 검사는 실제 입력 영역의 Windows 자식 창을 포함하지 않았다.

## 원인과 변경

운영 앱은 사용자 지시에 따라 High 무결성으로 실행된다. Chromium의 OLE 대상 해제와 최상위 창의 파일 메시지 허용만으로는 입력 영역을 덮는 `Chrome_RenderWidgetHostHWND`의 수신이 검증되지 않는다. 동일한 숨김 Electron 앱에서 기존 코드의 실제 렌더러 자식 창에 HDROP을 전달하면 preload의 파일 이벤트와 이미지 표시가 발생하지 않는 것을 재현했다.

`native/windows-file-drop`의 작은 Windows DLL이 현재 프로세스·UI 스레드에 속한 최상위 창과 Chromium 렌더러 자식 창을 동기적으로 subclass한다. 각 창에 파일 메시지 두 개만 허용하고 파일 수신을 등록한다. 받은 HDROP 좌표를 루트 클라이언트 좌표로 바꾸고 소유한 핸들만 내부 메시지로 Electron에 전달한다. 원본 메시지는 소비하고, 핸들은 성공·실패·창 종료에서 한 번만 해제한다. JavaScript FFI 콜백을 WindowProc으로 사용하지 않는다.

Electron의 공통 파일 읽기 → 실제 preload/contextBridge → 기존 첨부/프로젝트 초안 경로를 사용한다. 내부 탭·파일 드래그 중에는 Chromium OLE 대상을 복원하고 네이티브 수신을 잠시 끈다. 탐색기 수신으로 돌아오면 다시 활성화하며 렌더러 재생성 후 재등록한다. 관리자 실행, 앱 권한·질문하기·조건 확인 모드, 데이터 위치를 변경하지 않는다.

개발 실행기는 DLL을 먼저 빌드한다. Windows 배포 빌드에는 대상 아키텍처의 DLL을 `resources/windows-file-drop`에 포함한다. 빌드는 CMD와 MSVC를 사용하며 PowerShell을 호출하지 않는다. x64 빌드와 PE 아키텍처를 확인했고 ARM64 실행은 이번 환경에서 검증하지 않았다.

## 검증 범위

- 기존 코드: 실제 컴파일된 preload를 사용하는 숨김 Electron의 렌더러 자식 창에 전달한 경우 이미지 표시 실패를 재현.
- 수정 코드: 일반 권한의 별도 프로세스(Medium)에서 관리자 숨김 Electron(High)의 실제 렌더러 자식 창으로 파일 메시지를 전달하여 한 번의 수신과 이미지 decode 확인.
- 실제 T3 격리 데스크톱: 작성 입력창, 현재 프로젝트 목록, 관제센터에서 프로젝트 목록을 통한 초안 복귀, 파일 선택 입력의 공통 경로에서 이미지 미리보기 표시 확인. 실제 preload를 사용하며 브리지를 대체하지 않음.
- 프로젝트 초안 보존, DOM 드롭, 첨부 제거·8개 제한·좁은 화면은 별도 headless 웹 회귀 검사로 확인.
- 파일을 놓는 검사에서 provider turn 전송은 0건. 운영 DB에 테스트 데이터를 쓰지 않음.

증거는 작업 폴더 `.t3/dragdrop-visible-preview-20261023`에 보관한다. `bridge-child-old-error.txt`는 이전 코드의 실패, `bridge-child-integrated-medium-proof.json`과 `electron-drop-proof.json`은 수정 코드의 통과 증거다. 테스트 창은 숨김 상태로 유지했고 운영 앱의 창·입력을 자동 조작하지 않았다.

실제 사용자의 탐색기를 마우스로 끌어놓는 동작은 입력 탈취 금지 지시에 따라 수행하지 않았다. 이 검증은 Windows 메시지 수신부터 실제 작성창의 이미지 표시까지를 포함하며, 물리적인 드래그 제스처의 성공을 직접 확인했다는 뜻은 아니다.
