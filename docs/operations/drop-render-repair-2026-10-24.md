# Windows 이미지 드래그 미리보기 재신고 — 2026-10-24

## 확인한 사실과 남은 범위

사용자가 50MB 첨부 업데이트 뒤에도 드래그한 사진이 표시되지 않는다고 다시 신고했다. 기존에 남긴 새 대화 초안 중심의 검증만으로 사용자의 실제 파일·현재 화면까지 해결됐다고 판단할 수 없다.

운영 프로세스의 기록에는 02:47:40, 42, 44, 47 KST에 네이티브 드롭 수신 4회, 각각 파일 1개가 있었다. Windows 수신 단계까지만 확인되며, 당시 코드에는 렌더러 전달·초안 반영·이미지 로드에 대한 영수증이 없었다. 원래 신고한 파일의 이름·형식·용량은 아직 확인되지 않았다. 아래 수정으로 그 특정 파일의 문제가 해결됐다고 확정하지 않는다.

운영 창과 렌더러 자식 창의 파일 수신 등록, 관리자 토큰, 서버 상태를 읽기 전용으로 확인했다. 일반 PNG는 격리된 기존 대화에서도 작성창·대화 화면·프로젝트 목록 세 경로가 동작했다. 따라서 기존 대화라는 조건만으로 원인을 단정하지 않았다.

## 재현한 결함과 변경

1. 기존 네이티브 판독기는 파일 확장자 목록으로만 MIME을 정했다. JFIF 사진을 `application/octet-stream`으로 보내 일반 파일 카드가 나오는 것을 실제 이전 판독기의 결과와 작성창에서 확인했다. JPEG·PNG·GIF·WebP의 매직 바이트를 먼저 확인하고, JFIF 등 누락된 이미지 확장자도 보완했다. 알려진 확장자가 없는 JPEG도 이미지로 분류한다.
2. `elementFromPoint`의 첫 요소가 포털 툴팁이면 실제 첨부 영역을 찾지 못했다. 기존 첫 요소가 툴팁인 상태를 재현하고, 아래 요소까지 검사하도록 수정했다. 입력을 막는 모달을 통과해 뒤의 대화에 첨부하지 않는다. 좌표가 잘못되거나 대상이 없을 때 조용히 버리지 않고 안내한다.
3. 네이티브 대화 드롭을 즉시 CustomEvent/컴포저 ref로만 전달하던 경로를, 프로젝트 드롭과 같은 대상별 첨부 대기열로 통합했다. 컴포저가 준비될 때 해당 대화 초안이 수신한다. 파일을 읽는 동안 URL이 달라진 경우에는 종전처럼 재첨부 안내를 하므로 다른 대화에 자동으로 넣지 않는다.
4. `renderer.received`, `renderer.queued/rejected`, `composer.rendered`, `image.loaded/failed`를 주 창 IPC에 보고한다. 창의 실제 main frame 발신과 공유 스키마를 확인하며, 파일 개수·단계·정해진 이유만 기록한다. 경로·원문·이미지 바이트를 진단 로그에 넣지 않는다. `image.loaded`는 이미지 로드 이벤트이며 운영 화면의 픽셀 표시를 모두 증명하는 값으로 해석하지 않는다.

50MiB 파일당·합계 제한과 이미지 전송 압축, 사용자 권한·계획·질문하기·조건 확인 선택을 유지한다. 앱 권한이나 Windows UAC 설정은 바꾸지 않았다. 수신 DLL과 Windows 메시지 허용 범위도 이번에 변경하지 않았다.

## 검증

- 집중 테스트 9개 파일 68개 사례. 이미지 판독, Windows 수신, 데스크톱 창, 첨부 대상 탐색, 프로젝트 대기열, 작성창·선택·크기 제한·압축 회귀를 검사했다.
- 계약·데스크톱·웹 타입 검사와 변경 파일 lint·format, 웹 빌드를 검사했다. 저장소 전체 검사와 모바일 전체 검사는 실행하지 않았다. 모바일 동작은 변경하지 않았다.
- 실제 컴파일된 preload와 수신 경로에서 Medium 검증 프로세스가 High 격리 Electron의 렌더러 자식 창에 파일을 전달했다. 가져온 대화 기록이 있는 기존 대화를 사용했으며 실제 제공자 턴을 제출하지 않았다. JFIF, 확장자가 다른 JPEG, 툴팁에 가린 작성창, 기존 프로젝트, 기존 작성창에서 이미지 디코딩과 화면 캡처를 확인했다. 모달 차단도 확인했다.
- 첫 통합 실행의 마지막 화면 캡처가 18초 제한에 걸렸다. 이미지 로드 이후 캡처 단계의 실패였으며 원인을 확정하지 않았다. 동일 제품 소스로 캡처 제한 30초·애니메이션 정지 옵션을 적용해 전체 통합 검증을 다시 수행했다. 실패 기록도 보관한다.
- 빌드된 웹은 headless 브라우저와 제어된 드롭 DTO로 대기열·툴팁·렌더링 및 단계 보고를 검증한다. 이 브라우저의 DTO는 실제 Explorer 제스처로 표시하지 않는다.

증거와 이전 소스 해시·백업·집중 검사 로그·캡처·배포 및 완료 영수증은 `.t3/drop-render-repair-20261024/`에 보관한다. 실제 파일 탐색기를 마우스로 조작하는 검증은 사용자 입력 금지 지침 때문에 수행하지 않았다. 운영 교체는 기존 관리자 실행기로 web/backend/desktop을 실행하고 비활성 표시·실제 렌더링·데이터 홈·설정 보존을 확인한다.
